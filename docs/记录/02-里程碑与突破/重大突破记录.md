## 二、最大的一次单点提速：**日志**（10-30 19:30）

| 项 | 数值 |
|---|---|
| 修改前 | **8.60 fps**（文件夹 87） |
| 修改后 | **12.43 fps**（文件夹 93） |
| 提升 | **+45%** |

**发现：** `log_level` 是个**假开关** —— Switch 分支的 `REX_LOG_IMPL` 里写着 `(void)(cat);`，

**连带效果：**

| 指标 | 修前 | 修后 |
|---|---|---|
| `dentro_GPU` 占比 | 97.9% | **45.6%** |
| `MakeCoherent` | 8.9 ms/次 | **0.0005 ms/次** |
| 日志大小 | 900 KB | 100 KB |

**这是整个项目里性价比最高的一次改动**（3 行代码，+45%）。

## 三、把「慢在哪」量清楚（10-30 20:55 → 21:02）

| 时间 | 发现 | 数据 |
|---|---|---|
| 10-30 20:55 | PREP3 计时生效（`vert` / `tex` / `shader` 三段） | 文件夹 (103) |
| 10-30 21:02 | **爆发窗口不是对象创建，是"读被监视的 guest 内存"** | `tex=1470…7964 ms` 而 `creados tex=0 rt=0 pip=0` |

**结论：** Switch 上 `svcSetProcessMemoryPermission` 返回 `0xD401`，
无法做"只读监视"，SDK 只能**取消映射**代替 → **每次读被监视页的 4 字节就是一次 CPU 异常**。
上传一张纹理要读几 MB → 几秒。

## 四、两次"看起来能救、实际不行"的尝试（10-30 21:13 / 21:27）

| 版本 | 做法 | 结果 |
|---|---|---|
| 版本 11（105） | 纹理上传前整段解除监视 | `tex` 7964→26 ms，但 `vert` 14.6→431 ms，**fps 12.02→5.63** |
| 版本 13（106） | 改良：只解除已保护页、连续段 | 仍 `vert=442 ms`，**fps 5.52** |

**根因：** 每次上传都要扫全表并拿全局锁 → 顶点路径被串行化。
**教训：这条"按需解锁"的路走不通，必须换渲染实现。**

## 六、SD 卡被写坏（10-30 约 22:50，我的责任）

**原因：** 我给管线缓存加的"每 24 个管线保存一次"是从**任意工作线程**调用的，
多个线程同时对同一文件 `fopen/fwrite/fclose`，把 FAT 表写坏。

**症状：**

```
cache\shaders 里出现 65 个垃圾文件（名字是日志碎片，大小几 GB）
game_root、logs、user 目录变成"文件或目录损坏且无法读取"
普通删除无效（文件名含非法字符，Windows 无法寻址）
```

**修复：** 删除周期性保存；只在 `Shutdown` 单线程写一次并加互斥锁；后改为完全只读。
**卡的恢复：** 管理员 `chkdsk F: /f` 或格式化后从 `完整部署包\` 重拷（6.85 GB）。

## 七、三个数字把瓶颈定死（10-30 23:37 → 23:49）

| 时间 | 测量 | 结果 |
|---|---|---|
| 10-30 23:37 | **菜单最高帧率** | **18.69 fps**（1409/1410 帧，52 绘制/帧，超频 + native） |
| 10-30 23:49 | **跳过全部绘制** | **61.74 fps（16.2 ms/帧）** |
| 对照 | 正常绘制 | 0.46~0.59 fps（1703~2153 ms/帧） |

**结论（整个项目最重要的一条）：**

> **关卡内 99.2% 的帧时间花在绘制上。**
> **每次绘制 ≈ 0.42 ms；游戏逻辑/加载/音频/物理全部能跑满 60 fps。**

**参考项目的原生渲染器是 1.5~1.8 µs/绘制** → 5142 × 2 µs ≈ 10 ms → **60 fps 可达**。
**所以自写渲染器不是"优化方向之一"，是唯一的路。**

## 九、小绘制的真实形态（10-31 00:08）

```
NATIVO DIBUJO: pequenos=46000  con_handle=46000
    (ultimo: n=1  v=1  tipo=0  prim=1  handle=0xFFFFFFFFFFFFFFFF)
```

**发现：**

1. `tipo=0` = **没有索引缓冲** → 这些绘制走 `CmdVkDraw`（非索引），不是 `CmdVkDrawIndexed`
2. **每个 UI 四边形只有 1 个顶点** → 顶点着色器里展开成方块
3. `handle = 0xFFFF...FFFF` = 无效（因为没有索引缓冲）

**这解释了之前所有困惑：** 为什么索引不指向顶点缓冲、为什么 16 个 fetch 槽位全是 0。

## 十、顶点读取三次失败 → 找到正确接口（10-30 22:56 → 23:44）

| 版本 | 做法 | 结果 |
|---|---|---|
| 18 | `TranslatePhysical(addr)` | 读全 0 |
| 19 | 去掉 `<<2` | 读全 0 |
| **20** | `TranslateVirtual(addr<<2)` + 裸指针 | **崩溃**：`Unhandled guest access violation: read of guest 0x80400002` → 黑屏 |
| 24 | 加 `& 0x1FFFFFFF` 掩码（照 MW1 参考项目） | 不再崩，但仍读 0（槽位不对） |
| — | **最终结论** | **顶点格式不在 fetch 常量里**（它只有 type/address/size 共 8 字节），**手工解析 guest 内存这条路根本走不通** |

**正确接口（已实现）：** 在 SDK 的 `IssueDraw` 里、`PrimitiveProcessor::Process()` 之后
取 `primitive_processing_result` —— 里面是**已经解码好的**索引/顶点数据。新增
`sdk/include/rex/graphics/vulkan/nativo_hooks.h` 传递这个信息。
