# 第一部分：从 XEX 到 PC 上能玩

## 1. 项目准备：第一件事是把 XEX 变成 C++

### 1.1 素材

| 东西 | 规格 |
|---|---|
| 游戏 ISO | `COD6_MW2_Xbox360_ZH(1).iso`，6.81 GB |
| 解包后 | 151 个文件（86 个 `.ff`、55 个 `.bik`、5 个 `.pak`） |
| 可执行文件 | `default.xex`，5,029,888 字节 |

### 1.2 重编译（阶段 1-2）

```
rexglue codegen → 131 个 C++ 文件 / 62.9 MB
                → 19,283 个函数
```

生成的是一个标准 CMake 工程，链接 ReXGlue 运行时就能跑。

**第一道坎：中文路径。**

```
rexglue init 遇到中文路径直接崩，退出码 0xC0000409
```

把游戏文件复制到纯英文路径 `D:\rexglue-in\cod6\` 就正常了。

**这个坑后来又被验证了一次**（见 8.3），确实是 ReXGlue 的问题，不是游戏数据的问题。

### 1.3 overrides.toml：未解析分支的修正

重编译器不是万能的。有些地址它无法判断是不是函数入口（比如被 `bctr` 间接跳转到的），
需要在 `overrides.toml` 里手工声明：

```toml
[functions]
"0x8209CFC8" = { name = "sub_8209CFC8" }
```

第一条就是这样加的 —— 启动就崩：

```
[FATAL] Call to invalid or unregistered function at guest address 0x8209CFC8
```

### 1.4 教训

**重编译不是"一键完成"。** 出来的是 19,283 个函数，但"哪些地址真的是函数入口"需要人工/工具补齐。
`overrides.toml` 是这类项目的标配。

## 2. 环境地狱：四次换血才跑起来

这一节是全项目最耗时间的部分，也是最容易误判成"代码 bug"的部分。

### 2.1 换血一：WSL1 → WSL2

同一个 exe，两个结果：

**WSL1：死循环，10 分钟零输出，CPU 98%，RSS 15 MB**

```
BaseHeap::AllocFixed failed to alloc range from host
Failed to allocate function table at 83F00000
Failed to initialize guest memory function table
```

**WSL2：正常启动**

```
[sys]  Guest memory arena mapped: virtual base 0x100000000, physical base 0x200000000   ✅
[core] Function table initialized for module: code=82090000-824024C4, image=82000000-83F00000
[core] SDL input driver initialized successfully
```

**结论：ReXGlue 必须 WSL2。** WSL1 的内存映射语义（伪文件系统模拟）不支持客户机地址空间那套 mmap 布局。

> 这个是第一个"看起来像代码 bug、实际是环境"的例子。

### 2.2 换血二：Debian 12 → Ubuntu 24.04

预编译的 Linux SDK 需要 `GLIBCXX_3.4.31` / `3.4.32`：

| 系统 | glibc | libstdc++ | 能用吗 |
|---|---|---|---|
| Debian 12 (bookworm) | 2.36 | 3.4.30 | ❌ |
| **Ubuntu 24.04** | **2.39** | **3.4.33** | ✅ |

Debian 12 拿不到 3.4.31+（backports 里没有 `g++-13`），所以整个 WSL 发行版换成 Ubuntu 24.04。

### 2.3 换血三：GCC → clang-18（最隐蔽的一个）

用 GCC 编的时候，`generated/default/cod6_pch.h` 里这个宏**静默失效**：

```c
#define DEFINE_REX_FUNC(name)                          \
  __attribute__((alias("__imp__" #name)))              \
  __attribute__((weak, noinline)) extern "C" REX_FUNC(name);
```

每个函数体定义成 `__imp__sub_XXXX`，再用 `alias` 造一个 `sub_XXXX` 别名。
**GCC 把这个 alias 吞掉了**（对象文件里只有 281 个 T 符号、5 个 W 符号），于是：

```
19081 个函数体生成了
18844 个 undefined reference to sub_XXXX
```

换成 **clang-18** 后一次链接通过。

> **SDK 文档写"needs clang >= 18"不是随便写的。**
> 这个坑后来在 Switch 侧又出现了一次（见 11.4），只是那次是反过来 —— 只有 GCC 可用，得手工补分支。

### 2.4 换血四：工程不能跨平台搬

`generated/default/codegen.d` 是 Windows 版 rexglue 写的依赖文件，里面全是 `D:/...`：

```
target pattern contains no '%'. Stop.
```

而且构建时 `rexglue.cmake` 的 `add_custom_command` 会**强制重跑 codegen**，
而 Linux 版 rexglue 在 WSL1 里跑不了（`Unable to allocate XEX memory`）。

解法：
1. C++ 在 Windows 上生成好，再同步到 WSL
2. 把重跑 codegen 的那条 `COMMAND` 换成 `cmake -E true`

### 2.5 两个"假崩溃"

| 问题 | 症状 | 修复 |
|---|---|---|
| 缺 `libasound.so.2` | `SDL_InitSubSystem(SDL_INIT_AUDIO) failed`，紧接着就是 guest 0x3C 违例 | `apt install libasound2t64 libpulse0` |
| `/dev/shm` 被残留 arena 占满 | 每次 `kill -9` 泄漏一个 **4.8 GB** 的 `/dev/shm/xenia_memory_*`；满了以后 mmap 被截断 → **SIGBUS**，看起来像莫名崩溃 | 每轮测试前 `rm -f /dev/shm/xenia_memory_*`（已写进测试脚本） |

**这两条污染过之前的多次实验。** 你以为是代码问题，其实是上次崩溃的残留。

### 2.6 教训

**"环境层 bug 会完美伪装成代码 bug"。** 判断方法：
- 换一个环境（WSL1→WSL2、Debian→Ubuntu）行为变了 → 环境问题
- 每次测试前清理状态后行为变了 → 状态残留问题

## 4. 0x3C 空指针风暴：1261 万次违例

### 4.1 现象

```
Unhandled guest access violation: read of guest 0x0000003C
```

`0x3C` = 60，是结构体偏移 60 字节处 —— **典型的空指针解引用**。

违例率：单核 ~33,000 次/秒，多核 ~70,000 次/秒（随线程数翻倍 → 多个客户机线程同时空转）。

**截图全是纯黑，进程不退出。**

### 4.2 第一个关键实验：加一行 fprintf 就不崩了

在可疑函数 `sub_820BA528` 入口插入打印：

```c
fprintf(stderr, "[DBG] sub_820BA528 r3=0x%08X f48=0x%08X\n",
        ctx.r3.u32, ctx.r3.u32 ? REX_LOAD_U32(ctx.r3.u32 + 48) : 0xFFFFFFFFu);
```

结果：

```
[DBG] sub_820BA528 r3=0xA4821480 f48=0xBFB980D4
（6 次调用，全部是有效指针，跑满 40 秒没崩）
```

**去掉探针：6/6 次都在 0x3C 上死循环。加上探针：一切正常。**

→ **症状随时序变化**。这指向竞态或者内存破坏，不是"初始化没跑"。

### 4.3 用 perf 看清了 CPU 在干什么

```
perf record -F 499 -p <pid>   →  15408 个采样
落在 cod6（重编译代码）内的：1 个
CPU 热点：llvmpipe 线程（LLVM JIT 着色器编译）+ 内核锁
```

**CPU 几乎全花在软件 Vulkan（lavapipe）JIT 编译着色器上，不是在跑游戏代码。**

那个 guest `0x3C` 空转，是**游戏在等 GPU 排空 ring，而软件渲染器卡在编译着色器**。

> 这个观测非常重要 —— 它说明"CPU 满载、显卡空闲"不是代码问题，是**没有硬件 Vulkan**。

### 4.4 定位到具体循环

gdb 反复采样 25 次，**每次都在同一地址**：

```
sub_820BA240 + 1351     （cod6_recomp.37.cpp:1694）
指令: movl $0x310a0000,(%rbx,%rdx,1)      ← 往 ≈0x3C 写 GPU 命令字
```

数据流追出来了：

```
sub_820BA240:
    ld r10,11832(r3)        ← 设备对象 +11832 读 64 位「命令缓冲区」
    ...
    stwu rX,4(r11)          ← 从这个指针往前推进写 PM4 命令
```

- **只有一个写入者**：`sub_820CBF40`（`std r9,11832(r3)`）
- **只有一个读取者**：`sub_820BA240`
- 实测：设备 `0xA4821480` 的这个字段初值是 **`0xFFFFFFFF`**，之后被写成 **`0x30`**

### 4.5 关键发现：`0xFFFFFFFF` 是"未初始化"哨兵

```c
// li r11,-1 ; clrldi r28,r11,32        → r28 = 0xFFFFFFFF
// cmpld cr6,r10,r28 ; bne cr6,0x820ba27c
if (ctx.r10.u64 != 0xFFFFFFFFull) goto loc_820BA27C;   // 不等于才走"有缓冲区"路径
```

**字段是 `0xFFFFFFFF` 时本来该走另一条路** —— 但实际仍然进了写循环。
说明**分支判断出了问题**，或者 `+10942` 那个标志位不对。

### 4.6 硬件写断点：抓到了真凶

```
watch *(unsigned int*)0x183E4E9AC     ← 客户机 0x83E4E9AC + base 0x100000000
```

抓到两次写入：

```
sub_82095228 + 513   → 写入 0x83E4E9AC = 0x6C808DA4   （有效指针，初始化成功）
sub_82095330 + 4871  → 写入 0x83E4E9AC = 0x0          （清零）
```

**游戏在初始化后拆掉了自己的渲染子系统（虚析构），但工作线程还在继续使用它。**

```
工作线程 sub_820AF938 → lwz r10,-5716(r27) = 0
                     → lwz r11,60(r10)  = 读客户机地址 0x3C   ← 每秒 7 万次
```

### 4.7 从内存里挖出 PPC 镜像（工具突破）

ReXGlue 不提供 image dump，但**客户机镜像就在内存里**：

```
客人 0x82000000 → 宿主 0x182000000   （base 0x100000000 + VA，1:1）
dump 0x182000000 起 31 MB → /opt/dump/cod6_image.bin（以 "MZ" 开头）
```

有了它，`switch_check.py` / `find_gaps.py` / `pointer_audit.py` 这些工具**全部可用了**。

**这是个可复用的手法：静态重编译项目需要原始镜像时，直接从运行时内存 dump。**

### 4.8 排除了什么（都带证据）

| 怀疑 | 结论 |
|---|---|
| 游戏文件损坏 | ❌ ISO 内 152 项逐个比对，151 一致（差的 1 个是目录项）|
| 跳转表被截断 | ❌ `switch_check.py`：truncated 0 / wrong targets 0 / missed 0 |
| 生成代码翻译错 | ❌ 逐条对照 PPC 与 C++：空指针检查、`rlwinm.` 的 CR0 更新都正确 |
| 分配器返回 0 | ❌ 探针显示返回有效指针 `0xBFB9C0xx` |
| `VdGetSystemCommandBuffer` 返回假地址 | ❌ 反汇编确认 `0xBEEF0000` 是 **Xenia 故意为之** |
| gap 是漏翻译代码 | ❌ 180 个候选全在 code region 外（对齐填充）|
| 竞态 | ❌ 单核 `taskset -c 0` 仍稳定复现 |
| GPU 插件有问题 | ❌ 不加载插件行为完全一样 |
| 音频缺失导致 | ❌ 装好 ALSA 后音频错误消失，崩溃依旧 |
| 中文路径 | ❌ 复制到纯英文 ext4 路径，行为完全一致 |

**十项排除，每项都有硬数据。**

## 5. 决定性修复：setjmp / longjmp

### 5.1 问题本质

MW2 在 `Com_Error` 恢复时用 `longjmp` 跳回 `setjmp`。
**静态重编译无法跳进 C++ 函数中间**，所以这两个函数必须交给运行时的
`ppc_setjmp` / `ppc_longjmp` 处理。

**没声明时，guest 的 longjmp 会从过期的 LR 返回，把栈指针一路往上抬：**

```
正常: sub_82283648 入口 r1 = 0x7015FD40 → stwu -208 → 0x7015FC70 ✓

故障: 同一条链，r1 整体高 0x350 → r1 = 0x7015FFC0，栈顶 0x70160000
      → 可变参数函数存 r5..r10 到 r1+0x40 = 越过栈顶 = 护栏页
```

这条是 bo2zm-nx 移植在 overrides 里写下的经验：
> 没有它们，第一次启动 3 秒就写坏内存。

### 5.2 怎么找到这两个函数（可复用手法）

1. **setjmp**：在镜像里扫「以 r3 为基址、连续 `stfd fX` + `std rX`」的函数
   → 存 f14-f31 到 0..136(r3)、r13-r31 到 152..296(r3)、再用 `stvx128` 存 v64-v127
2. **longjmp**：扫它的镜像（连续 `lfd` + `ld`）
3. **关键一步：用 `bl` 目标核对**

**我在这里犯过一个错：** 一开始把 setjmp 写成 `0x823DFF08`（上一个函数的尾巴），
结果 codegen 生成了 23 处 `ppc_longjmp` 却**零处 `ppc_setjmp`** →
运行到 longjmp 时找不到已注册的 jmp_buf → **直接 abort（退出码 134）**。

扫 `bl` 目标后确认真实入口：

```toml
setjmp_address  = 0x823DFF10    # 被调用 14 次
longjmp_address = 0x823E08C0    # 被调用 22 次
```

### 5.3 结果

```
生成: ppc_setjmp 14 处、ppc_longjmp 23 处
运行: 违例 0 ✓   不再 abort ✓   三条图形管线建立 ✓   音频正常 ✓
```

**1261 万次违例 → 0。栈破坏与空转风暴彻底消失。**

## 7. 网络补丁 netshim.c：画面出来了

### 7.1 先走错的路

最初的做法是**逐条给网络函数打桩**（在 guest 代码里改）。这制造了两个新 bug：

- `XNetGetTitleXnAddr` 返回 0 让 `loc_8230FA34` 变成 do/while 死循环（占 12.8% CPU）
- `WSAStartup` 打桩没填 `WSADATA` 让版本号读成 21.112

**方向错了：不该改游戏代码，该在宿主边界改。**

### 7.2 正确做法：LD_PRELOAD 拦 socket

```
bind      → 总是返回成功（"WARNING: Couldn't allocate IP port" 消失）
setsockopt→ 总是返回成功（"Failed to set socket to broadcast-capable" 消失）
recvfrom  → 强制 MSG_DONTWAIT，没数据就返回 0
ioctl/connect/listen/sendto/accept → 同样兜底
```

### 7.3 最后一块拼图：两条规则

之前所有版本都错在同一个地方 —— **改了不该改的 socket**。

| 规则 | 错误做法（导致黑屏） | 正确做法 |
|---|---|---|
| **`recvfrom` 没数据时返回什么** | 返回 `-1` + `EAGAIN` → 游戏判定为致命错误 → `Com_Error: "Failed to recvfrom() socket, error %s.."` → longjmp → 重启/退出 | **返回 `0`**（空数据报）。游戏只检查负数，0 表示"暂时没数据" |
| **改哪些 socket** | 改**所有** socket → SDL 的 X11 连接（unix socket）被假装成功 → `SDL_InitSubSystem(SDL_INIT_VIDEO) failed: x11 not available`，**窗口都开不出来** | **只改 `AF_INET`/`AF_INET6`**，unix socket 一律放行（`getsockname` 判断） |

**这两条一改，画面立刻出来。**

```
[2026-10-27 22:1x] 跑 60 秒：
  10s 亮度=0.037   最大=0.690   （版权页）
  20s 亮度=0.391   最大=0.996   （MODERN WARFARE 2 + 按下START）
  60s 亮度=0.383   最大=0.996
  Com_Error=0   图形管线=12   违例=0
```

截图在 `frames\r34_fixed\`、`frames\r35_menu\`（后者能看到 LOGO 在逐帧左移 = 实时渲染）

### 7.4 完整的必要条件链

| 编号 | 内容 | 没它会怎样 |
|---|---|---|
| **P1** | 虚析构改空操作 | 工作线程读已释放对象，0x3C 空转 7 万次/秒 |
| **P2** | 网络初始化返回成功 | `Com_Error: "Failed to set socket to nonblocking"` |
| **P3/P4** | 全局为 0 时保护 / 不再清零 | 同上 |
| **P8** | 忽略 `XamLoaderLaunchTitle("default.xex")` 请求 | 游戏 6~9 秒后请求重启自己，运行时当成结束 → `Execution complete` 退出 |
| **setjmp/longjmp** | overrides 声明两个地址 | 23 处 longjmp 跳回过期 LR → 栈指针往上爬 → 1261 万次违例 |
| **netshim** | 见上表 | 黑屏 |

## 8. 软件渲染（lavapipe）与真正的黑屏原因

### 8.1 一个必须说清楚的事实：PC 上是纯软件渲染

**WSL2 里没有硬件 Vulkan：** NVIDIA 只提供 CUDA/D3D12，Mesa 的 `dzn`（D3D12 后端）没编进去，
所以只有 **lavapipe**（纯 CPU 软件 Vulkan）。

这就是为什么会看到「CPU 满载、显卡空闲」—— **不是代码问题，是没有 GPU 加速**。

参考项目的 PC 参考渲染器用的是 **Direct3D 12**（Windows 原生），
我们走的这条路是**最边缘的配置**。

### 8.2 帧率与性能的真相

| 观测 | 数据 | 含义 |
|---|---|---|
| `VdSwap` 调用 | 60 秒 **121 次** | 帧循环在跑（约 2 FPS）|
| 图形管线 | 只有 3 条 | 菜单需要几十条 → 游戏几乎没提交绘制 |
| perf 采样 | 无单一热点 | 主线程是**阻塞等待**，不是在算 |
| 打开的数据文件 | `common.ff` `ui.ff` `code_post_gfx.ff` `patch.ff` + 4 个 `.pak` | 确实在读游戏数据 |

**2 FPS 的软件渲染** —— 这个数字很重要，它说明"能跑"和"能玩"是两回事。

### 8.3 一个早期的黑屏排查：已证明 vs 已排除

**已证明（有硬数据）：**

| 事实 | 数据来源 |
|---|---|
| 帧循环在跑 | `VdSwap` 探针：60 秒 121 次 |
| 游戏只提交过约 3 次绘制 | 「Creating graphics pipeline state」只有 3 条 |
| 渲染器初始化**返回了** | 二分探针：三个调用都正常返回 |
| 游戏在 6~9 秒后自己退出 | `Execution complete` |

**已排除：**

| 怀疑 | 结论 |
|---|---|
| 中文路径 | 复制到纯英文 ext4 路径，行为完全一致 |
| swapchain 格式不对 | format 44 = `VK_FORMAT_B8G8R8A8_UNORM`，正常 |
| Xvfb 缺 Present 扩展 | **有** Present、MIT-SHM，swapchain 创建成功 |
| presenter 的 cvar | 三种组合全试，仍黑 |
| `KeWaitForSingleObject` 是原因 | **不是** —— 只出现 6 次且在退出路径上 |

### 8.4 两个失败的工具尝试（教训）

**1. `vkshim.so`（LD_PRELOAD 拦 Vulkan）无效**
插件是 `dlopen` 后用 `vkGetDeviceProcAddr` 取函数指针。
把 `vkGetDeviceProcAddr`/`vkGetInstanceProcAddr` 也拦了仍然没用（dlsym 从 handle 取符号）。
**要真拦必须写 Vulkan layer**（implicit layer + `VK_LAYER_PATH`）。

**2. 在函数入口读 `r4` 永远读到垃圾**
那个字符串是**函数内部**才 `lis/addi` 进 r4 的。

### 8.5 音频与录制

- 运行时确实在推音频：`audio endpoint 'ALSA default playback device': 6 ch, 48000 Hz`
- 但 **WSL2 里没有声卡**（无 `/dev/snd`），ALSA 只能挂 null 设备 → **听不到、也录不到**
- 三条路都试过不通：ALSA `file` 插件不落盘、`SDL_AUDIO_DRIVER=dummy` 不被支持、`disk` 不生成文件
- **录屏可以**：每轮 6 帧 PNG + `contact.png` 拼图

## 10. 工具链：真正的 devkitPro 在 WSL 的 rootfs 里

### 10.1 Windows 的 devkitPro 不能用

### 10.2 真正的工具链在这里

```
D:\devkitPro\wsl\inst\rootfs\opt\devkitpro
```

## 11. SDK 与静态重编译：8 个环境层的坑

公开的 ReXGlue SDK **完全没有 Switch 支持**。Switch 后端在第三方 fork 里，我们最初用 `nfsmw-nx` 的。

### 11.1 依赖缺失

tarball 里的 `thirdparty` 是空的，需要 14 个 git 子模块。
从 codeload 按上游固定 SHA 下载，并伪造 `.git` 文件（CMake 用 `EXISTS .git` 判断）。

### 11.2 副本嵌套

`cp -rf src dst` 会变成 `dst/src`。正确写法 `cp -a src/. dst/`。

### 11.3 NTFS 符号链接变 0 字节

解压后 13 个符号链接变成 0 字节重解析点（`libmspack`/`cabextract`）。用真实文件替换。

### 11.4 19 万未定义符号（最重要的一个）

```
undefined reference to `sub_82345678`
... 十九万个
```

**原因和 2.3 是同一个，只是方向反了：** GCC 会在 `extern "C"` 之前**静默丢弃** attribute，
导致 19,283 个重编译函数的 section 属性全部失效。

PC 侧的解法是**换 clang**，但 Switch 侧只有 GCC 可用 —— 所以得**手工补 GCC 分支**：
把 `attribute` 放在声明符**之后**。

SDK 自己的 `pch_h.inja` 模板里就有这个分支，只是 PC 上生成的 `cod6_pch.h` 只有 clang 分支。

### 11.5 FFmpeg 的 `#error "no config"`

`config.h` 按平台分支，没有 Switch 分支。加：

```c
#elif defined(__SWITCH__)
#include "config_switch_aarch64.h"
```

并关掉 `HAVE_MMAP` / `HAVE_MEMALIGN` / `HAVE_POSIX_MEMALIGN`。

### 11.6 `bsf_list.c` 数组名错误

```c
static const AVBitStreamFilter * const bitstream_filters[] = { NULL};
```

### 11.7 `PTHREAD_ONCE_INIT` 未声明

加 `-D_POSIX_THREADS -D_UNIX98_THREAD_MUTEX_ATTRIBUTES`。

### 11.8 glslang / FFmpeg 需要 POSIX 垫片

`switch_compat/` 下补 `semaphore.h` / `sys/mman.h` / `sys/resource.h`。

### 11.9 教训

**上游 tarball ≠ 可用工程。** 子模块、符号链接、平台分支这些"环境层"问题，
每一个都会伪装成"代码 bug"，报错信息完全不指向真正原因。

## 14. 第一课：一个默认值为空的配置项

**这是整个 Switch 阶段最重要的一个发现，而且在第 12 轮才发现。**

### 14.1 现象

前面 11 轮的日志里，**从来没有出现过任何 Vulkan 相关内容**。

### 14.2 原因

```cpp
REXCVAR_DEFINE_STRING(gpu_plugin, "", "GPU",
```

## 16. 最顽固的根因：libnx 的互斥量不唤醒等待者

### 16.1 同一个根因撞了五次

1. `state_mutex_`（线程状态）
2. `global_critical_region`（对象分配）
3. `heap_mutex_`（客户机堆）
4. `state_mutex_`（Resume 路径）
5. 全局临界区（ABBA 的前半）

**现象永远是：两个线程争同一把 `std::recursive_mutex`，等待方永远醒不过来，全进程 0% CPU。**

### 16.2 怎么确认的

`probe_b.nro`（200 KB，纯 libnx）测了四件事：

```
std::mutex            ✓
std::thread           ✓
std::condition_variable ✓
join                  ✓
```

**单线程场景全过，但在真正竞争时会丢唤醒。**

### 16.3 为什么这是"工具链"问题

BO2 的移植用的是 devkitPro 官方 Docker 镜像，我们用的是从 rootfs 里拿的那份 ——
**两者 newlib 的 pthread 实现不完全一致。**

## 17. 自旋递归锁：自己造一个能用的

### 17.1 实现

```cpp
class SwitchSpinRecursiveMutex {
  void lock() {
    unsigned self = CurrentId();
    if (owner_.load() == self) { depth_.fetch_add(1); return; }   // 递归
    for (;;) {
      unsigned expected = 0;
      if (owner_.compare_exchange_weak(expected, self)) { depth_.store(1); return; }
      nanosleep(0.2ms);
    }
  }
  static unsigned CurrentId() {
    uintptr_t raw = (uintptr_t)pthread_self();
    return ((raw >> 4) & 0x7FFFFFFF) | 1u;    // ← 必须非零
  }
};
```

**关键点：**

- 不需要内核唤醒 → "等待方永远不被唤醒"不可能发生
- **线程号必须非零** —— 空闲值是 0，如果线程号也是 0，每把锁都会被当成"同线程重入"，
  加锁从不占用、解锁从不释放

### 17.2 本地验证（不需上机）

把类抽出来在 Linux 上跑：

```
[1] 单线程加锁 / 递归 / 解锁            ok
[2] 双线程竞争（每边 200 次）          计数器 == 400   ok
[3] 8 线程 x 5000 次压力               计数器 == 40000 ok
[4] 递归重入在竞争下仍正确             计数器 == 1000  ok
[5] 另一个线程 try_lock 必须失败       ok
=== 全部通过 ===（ThreadSanitizer 零告警）
```

**这个测试直接抓出了那个致命 bug**（`CurrentId()` 返回 0），省掉好几轮上机。

### 17.3 真机上的自检

```cpp

[spin] id=3681649872
[spin] selftest: ok
[spin] contention: starting
[spin] contention: done, counter=400 (expect 400)
```

**`cvar::Init` 对空 argv 调了 `strlen`。**

> *"Emulators (Ryujinx 1.1.1403) start NROs with null argv entries, and the command-line

Switch 的客户机内存用 `svcMapProcessCodeMemory` 造"代码别名"，Ryujinx 对 homebrew 返回 `InvalidHandle`。

## 20. 模拟器的天花板

```
Guest memory arena mapped: virtual base 0x9AF34E000, physical base 0xAAF34E000
                                              ↑ 相差 4 GB
崩溃: Invalid memory access at 0x0A2F34E000   ← 物理视图 + 2 GB
```

```cpp
// xmemory.cpp:190
virtual_membase_  = mapping_base_;
physical_membase_ = mapping_base_ + 0x100000000ull;   // 物理镜像 = 虚拟 + 4 GB
```

`MapViews()` 要求两个视图**在地址空间里连续**，所以最小需求：

```
4 GB（虚拟视图） + 4 GB（物理镜像） = 8 GB 连续地址空间
```

**Ryujinx 的 homebrew 进程最多给 6 GB**（`expand_ram: true` 也就到 6 GB）。

### 20.1 更根本的问题

即使内存够，模拟器也帮不上核心的忙：

**Ryujinx 用宿主线程实现 libnx 的 pthread，而宿主 pthread 是好的。**
真机上撞的那五处死锁，在 Ryujinx 上一次都不会出现 ——
`AllocRange` 在 Ryujinx 上从头到尾没卡过，就是这个证据。

**模拟器能验证"游戏逻辑对不对"，但验证不了"工具链的坑"。**

### 20.2 能不能让它跑起来

技术上可以：**跳过物理镜像**，让 `physical_membase_ = virtual_membase_`，
地址空间需求从 8 GB 降到 4 GB。

代价：
- 改动在核心内存层
- 真机上**不能**这么干（Xbox 360 确实有物理/虚拟别名），必须做成只在模拟器上生效的开关
- 风险中等

**判断：现在不值得。** 真机上卡的是明确的 ABBA 死锁，而且后面还有很长的路。

**PC 阶段也有同类问题**：`/dev/shm` 残留和缺 `libasound` 污染过多次实验，很久才发现。

### 21.2 方向错误：在错误的 SDK 上打补丁

一直用 `nfsmw` 的 SDK。后来对比 BO2 的：

```
src/core/threading_posix.cpp    我们 1675 行 / BO2 2561 行   ← 差 886 行
src/system/xthread.cpp          我们 1511 行 / BO2 1636 行
BO2 的 Switch 适配点 19 处 / 我们 13 处
```

**BO2 那份多了 886 行，我撞的每个坑它基本都填过了。**

用户一句"别的项目都是怎么弄的"点醒了我。

### 21.3 实现错误：自旋锁的线程号为 0

```cpp
static thread_local unsigned id = 0;   // 如果 TLS 初始化失败，永远是 0
```

空闲值是 0，线程号也是 0 → 每把锁都被当成"同线程重入" → 加锁从不占用、解锁从不释放。
**白白花了三轮（16/17/18）。**

### 21.4 判断错误：把"空锁"当成解决方案

第 14 轮把全局临界区改成完全不锁，结果卡点一模一样。
**空锁只是把问题推到更晚，还引入数据竞争风险。**
正确做法是换一个**能工作的锁**，而不是不要锁。

### 21.5 流程错误：换 SDK 时把修复弄丢了

第 8 轮整份替换 `sdk/src` 和 `sdk/include`，把"Switch 上日志绕过 spdlog"覆盖掉了。
结果日志停在 `early logging up`，比之前还早。

**教训：大范围替换之前，先列出必须保留的补丁清单。**

### 21.6 诊断错误：搜字符串方式不对

日志格式是 `[cod6] ctx: %s` + 独立的 `"enter"` 字面量。
我一直搜 `ctx: enter` 这个组合，得到假阴性，耽误了一轮。

### 21.7 工具错误：PowerShell 吃掉 bash 变量

```powershell
wsl bash -c "for f in $files; do ..."    # $files 被 PowerShell 吃掉了
```

**教训：带变量的 bash 一律写成脚本文件。**

### 21.8 表达错误：把"初始化成功"说成"画面出来了"

第 12 轮日志里有 `phase 8/9: ImGui drawer up (first frame is being drawn)`，
我说"第一帧出来了"，但实际上那只是**创建交换链**的日志，主循环根本没开始。

用户立刻指出"但是还是12号还是黑屏啊"。

**教训：图形栈初始化成功 ≠ 画面出来。** 只有日志里出现主循环开始、帧计数在涨，才算真的出画。

### 21.9 定位错误：把 setjmp 地址写成上一个函数的尾巴

`0x823DFF08` vs `0x823DFF10`。差 8 个字节，结果生成了 23 处 `ppc_longjmp` 却**零处 `ppc_setjmp`**，
运行到 longjmp 时直接 abort（退出码 134）。

**教训：用 `bl` 目标核对，不要靠"扫特征码看起来像"。**

### 21.10 工具尝试失败：vkshim.so 拦 Vulkan

LD_PRELOAD 拦不住 `dlopen` + `vkGetDeviceProcAddr`。要真拦必须写 Vulkan layer。

## 22. 方法论总结

### 22.1 有效的做法

| 做法 | 效果 |
|---|---|
| **对照探针**（probe_a / probe_b / probe_c） | 一次排除一大类可能，比改代码猜快十倍 |
| **阶段标记**（`[rt]` / `[cn]` / `[xc]` / `[ar]`） | 把"卡在某处"变成"卡在第 N 行" |
| **符号化崩溃地址** | 从"Invalid access 0x0"直接定位到 `strlen` |
| **本地验证纯逻辑** | 锁的正确性不需要上机，Linux 上跑就够 |
| **性能日志看 CPU%** | 0% = 死锁，100% = 死循环，一眼分清 |
| **硬件写断点** | `watch` 客户机地址，直接抓到写入者 |
| **从运行时内存 dump 镜像** | 没有 image dump 工具时，客户机镜像就在内存里 |
| **perf 无扰动采样** | 看出 CPU 到底花在哪（lavapipe 编译着色器，不是游戏代码） |
| **对比能跑的项目** | MW1/BO2 的配置和日志是现成的参考 |
| **宿主边界修而不是改游戏代码** | `netshim.c` 一次解决一类问题 |

### 22.2 无效的做法

| 做法 | 为什么无效 |
|---|---|
| 反复改代码 + 上机测试 | 没有对照，无法定位 |
| 空掉锁 | 只是把问题推后 |
| 全盘替换 SDK | 会丢掉已验证的修复 |
| 靠日志行"看起来对"判断 | 日志可能只是创建资源，不代表功能完成 |
| 逐条给系统调用打桩 | 制造新 bug，该在宿主边界修 |
| 在函数入口读参数寄存器 | 那个值可能是函数内部才算出来的 |

### 22.3 一个贯穿全程的规律

**每一个"看起来像游戏 bug"的问题，最后都是环境/工具链问题。**

三个阶段的例子：

| 阶段 | 问题 | 真正原因 |
|---|---|---|
| PC | 死循环、零输出 | WSL1 |
| PC | 19 万未定义符号 | GCC 的 `alias` 静默失效 |
| PC | 莫名 SIGBUS | `/dev/shm` 残留 |
| PC | 0x3C 空指针风暴 | 没声明 setjmp/longjmp |
| PC | 黑屏 | `recvfrom` 返回值 + 改了 unix socket |
| Switch | 整个渲染栈消失 | `gpu_plugin` 默认空字符串 |
| Switch | 五处死锁 | newlib 的互斥量不唤醒等待者 |
| Switch | 更早的卡死 | 自旋锁线程号为 0 |

**游戏代码本身的 bug 反而只有 P1-P4、P8 这几个（都是"游戏自己拆了东西"这类）。**

这说明 ReXGlue 的重编译质量是可靠的 —— 难的不是翻译，是**让翻译出来的东西在目标平台上跑起来**。

### 每一项的实测依据

**❶ 关掉 `full_texture_hash`（+48%）**

```cpp
// ChangeDetector
static constexpr uint32_t kTrustedChecks = 12;   // 连续 12 帧不变 → 信任
static constexpr uint64_t kFullEvery = 16;
static inline bool always_full = false;          // ← 打开后全部失效
```

`always_full = true` 会让**每帧每张纹理每个顶点缓冲全量哈希**，约 51 MB/帧。

它的自述里就写着 `Diagnostics:`。**是坏卡时期加的诊断补丁，卡好了就不需要了。**

**结果：9.2 → 13.6，贴图没有变坏。**

**❷ 纹理池预热（+16%）**

```cpp
// 原来：预算的一半，夹到 256 MB
const int32_t mb_inicial = std::clamp<int32_t>(mb_max / 2, 64, 256);

// 改成可配置
const int32_t mb_inicial =
    std::clamp<int32_t>(REXCVAR_GET(cod6_native_texture_pool_prewarm_mb), 64, mb_max);
```

预算 768 MB 却只预热 256 MB。游戏超过之后：

```
[native] pool de texturas: bloque 9 nuevo en caliente; ya van 320 MB reservados
```

**游戏中临时 `vkAllocateMemory(32 MB)`，主线程阻塞，GPU 掉零。**

改成 512 MB 预热后：**全程 `临时新建次数: 0`。**

**❸ 工作线程绑核（+1.3%，但最低帧 +23%）**

```cpp
svcSetThreadCoreMask(CUR_THREAD_HANDLE, 1, 0x3);   // 原来：核心 0、1
svcSetThreadCoreMask(CUR_THREAD_HANDLE, 2, 0xC);   // 改成：核心 2、3
```

**录制线程和游戏主线程抢同两个核，核心 2、3 完全闲着**（`CPU 199% / 400%`）。

改完：最低帧 6.9 → 8.5，最高 21.3 → 23.1。**平均只涨 1.3%，但卡顿明显减轻。**

**❹ 场景半分辨率（失败，−7.5%）**

```toml
cod6_native_scene_scale_percent = 50
```

日志：

```
[scene-scale] percent=50 enabled=true
             exclusions=host-msaa,menu,video,shadow,model-lighting
```

**最贵的几个 pass（阴影、模型光照）都被排除在缩放外。**

GPU 从 25~33 ms 变成 28~30 ms（几乎没变），却多了一次放大 blit。**净亏，撤回。**

### 这一段的三个发现

**1. `cod6_game_skip_depth_prepass` 是个空开关**

```toml
cod6_game_skip_depth_prepass = true    # ← 二进制里根本不存在
```

`cod6_render_hooks.cpp` 不在 CMakeLists 里，因为它的钩子绑定的是
**COD5 的地址**（`sub_82422508`、`sub_82405078`）。

**我一度把这个当成绩效提升的原因，是错的。第 250 轮的提升全部来自关哈希。**

**2. CPU 和 GPU 完全没有重叠**

```
renderer CPU  ~30 ms
GPU           ~30 ms
帧时间         62 ms    ← 是两者之和，不是 max
```

**正常应该是 `max(CPU, GPU) = 30 ms = 33 fps`。**

嫌疑：每帧末尾的硬同步点

```cpp
DrainRecorder();
EndPass();
textures.WaitForUploads();     // ← 等所有纹理上传完成
```

## 三、纹理诊断体系（第 303 ~ 308、320、324、325、326 轮）

依次加了：

| 轮次 | 加了什么 | 结论 |
|---|---|---|

## 四、关键突破：贴图数据本身是好的

把导出文件离线解码，用**正确的**格式：

| 贴图 | guest 格式 | 解码器 | 结果 |
|---|---|---|---|
| 沙鹰世界模型 | DXT4_5 | BC3 | 干净 |
| 桌面法线 | DXN | **BC5** | 干净的法线贴图（背景 R=G=128，边缘清晰） |

平滑度量化：按 BC3 误解时 **5.4**，按 BC5 正确解时 **324.3**，差 60 倍。

**从这一刻起，「贴图数据坏了」这个说法被彻底排除。**

## 五、被逐一排除的方向

| 假设 | 排除依据 |
|---|---|
| 贴图内容在变 | `hash: 0 cambio / 45178 igual` |
| 同一张贴图被重复上传 | `subidas` 计数，每张一次 |
| 显存池块复用 | `DestroyImage` 先销毁图像再归还块，结构上不可能别名 |
| 地址算错 | `[dtab]` 读的是实时寄存器，是游戏要的地址 |
| 影子副本过期 | 绑定路径 `GetView(regs->GetTextureFetch(slot))` 也是实时寄存器 |
| 绑定槽位错位 | 描述符从 binding 0 连续打包，与 SDK 一致 |
| 键值缓存碰撞 | 全键比较，碰撞只是换槽，不是错误答案 |
| DXN 通道顺序（RG vs RA） | 加了 `cod6_native_dxn_ra` 开关，实测无变化 |

## 六、PC 软解环境（这条支线终于走通）
