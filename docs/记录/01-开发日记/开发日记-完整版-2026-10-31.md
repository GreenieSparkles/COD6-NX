# 序：这件事到底在做什么

**目标**：把 Xbox 360 版的《使命召唤6：现代战争2》跑到 Switch 上。

**做法**（不是模拟器）：

```
① Xbox 360 的 default.xex  →  ReXGlue 反编译成 C++（131 个文件，62.9 MB）
② 那套 C++ 在 PC 上编译运行成功（验证逻辑正确）
③ 同一套 C++ 交叉编译成 ARM64 → 链接 SDK → cod6.nro
④ Switch 上：ARM64 原生执行 + Vulkan → Mesa/NVK → Tegra X1 的 GPU
```

**和 COD5/COD4 移植者的链路完全一致：**

```
ARM64 原生程序 → 自写渲染器 → Vulkan → Mesa/NVK → Switch GPU
      ✅             ⬜            ✅        ✅          ✅
```

**只剩中间那一环 —— 自写渲染器 —— 还在做。**

# 第二章 · 实机：前 50 次几乎全在打平台（10-23 → 10-29）

> 说明：最早的实验其实在 10-23，比 PC 版还早 —— 那一次只是为了验证
> 「Switch 上能不能自己调频 + 起 NVK」。

## 10-23 18:00 第 1 次

```
[apm] 调频成功
NVK 起来了
std::terminate: std::bad_alloc
```

**好消息：Switch 上 Vulkan/NVK 可用，能调频。**
**坏消息：堆没配够。**

## 10-28 上午：spdlog 死锁（第 4–7 次）

程序停在：

```
[cod6] ctx: calling logger->log
```

**根因**：spdlog 在 Horizon 上初始化时卡在 FILE 锁。
**修法**：换裸 `write(2)`。**第 8 次绕过成功，走到 phase 2/9。**

## 10-28 中午：10 次白跑，因为少了一个文件（第 10–19 次）

现象：`Too few processor cores`。

**真相**：卡上没有 `cod6.toml`，`gpu_plugin` 是空串 → **根本没加载图形插件**。

**第 20 次补上 `cod6.toml`（`gpu_plugin = "xenos"`）→ GPU 终于起来了，日志从 41 行暴涨到 166 行。**

## 10-28 下午到晚上：newlib 互斥量不唤醒 + ABBA 死锁（第 21–33 次）

- `state_mutex_` 争用后不唤醒 → `WaitStarted()` 卡住
- `heap_mutex_` 争用后不唤醒 → `SystemHeapAlloc` 阻塞
- `global_critical_region` 与 `heap_mutex_` 构成 **ABBA 死锁**

**中途还试错过**：把所有自旋锁换成标准锁、把 `State` 改成命名空间级全局 —— 都无效。
**这说明不是锁的问题（后来证明是 TLS）。**

## 10-28 深夜：两个硬约束浮出水面（第 35–38 次）

```
svcSetProcessMemoryPermission -> 0xD401        ← 页权限改不了
一次缺页吃两个异常槽位
```

**这两个发现决定了后面所有的技术路线**（见第四章）。

## ★ 第 39 次（10-28 23:08）：第一次加载客户机镜像

```
phase 3/9: loading guest image
Loading XEX image: game:\default.xex
  XEX image loaded successfully
phase 6/9: launching guest thread
[xt] Create: entry 0x82370938
```

**日志从 614 行暴涨到 1556 行，阶段从 2/9 跳到 6/9。**

修法是我加的 `RexGmMapCommittedNow()`（提交时就映射）。
**后来被官方文档否定，已删除 —— 这是我自己走了弯路。**

## ★ 第 47 次（10-29 00:44）：把"静默死锁"变成"带栈崩溃"

到第 46 次为止，程序既不崩也不动。**没有崩溃信息，只能在锁上瞎猜。**

**第 47 次终于拿到第一条有意义的崩溃：**

```
pc   imagen+0xc1514
instruccion 0xf9000073  =  str x19, [x3]
far 0x48
x3  0x48
```

**根因**：缺页交给 SEH，SEH 说"我处理了"，线程被放回原指令重试 → 再缺页 →
占下一个槽位 → 24 个槽位耗尽后**异常入口无限空转**。

**修法**：只有落在客户机窗口内的缺页才交给 SEH；宿主地址缺页直接打崩溃日志并退出。

**这是整个项目最重要的一次改动。** 没有它，后面三轮不可能有进展。

## ★ 第 50 次（10-29 01:53）：游戏真正跑起来了

```
Presenter: modo de pintado -> desde el hilo del juego
AudioSystem::RegisterClient: client index=0 queued_frames=8
Resolve: 0,0 <= x,y < 1280,720, k_8_8_8_8 at 0x1DF1E000
[rex] XELOG_GPU PRESENT: swap_texture_view=0x...
phase 7/9: guest thread running
```

**客户机在执行真实游戏代码、向 GPU 下命令、提交画面、播放音频。**

**根因（最久的一个）**：编译时缺 `-mtp=soft`。

```
mrs tpidr_el0     ← Horizon 上永远是 0，一读就崩
```

官方文档 `toolchain.md` 原文就写着这一条，**我没有第一时间照做，代价是六七轮。**

**修法**：`switch-devkitA64.cmake` 第 61 行加 `-mtp=soft`。

**剩下的问题**：只提交 1 帧（0.0 fps），然后自己 `TerminateTitle`。

## 前 50 次的代价与收获

**真正的根因只有六个：**

1. spdlog 在 Switch 上卡死
2. 缺 `cod6.toml`（10 次白跑）
3. newlib 互斥量争用不唤醒
4. libnx 异常槽位被泄漏
5. 我自作主张的"提交即映射"（加了又删）
6. **缺 `-mtp=soft`**（最久）

**教训：前 46 次慢，是因为没有崩溃信息。第 47 次让程序崩溃之后，三次运行就到了游戏运行。**

## 10-30 中午：黑屏三连（73–75），我自己造的


## 10-30 13:05 第一次有稳定画面（78 号）

**修的是 `protect_zero = false`：**

游戏代码里 `sub_821254B0` 会做 `lwz r11,44(r4)`，而 `r4` 是 NULL ——
**它在读零页上的核数据，这是 Xbox 360 的正常行为。**保护零页会让任务加载直接崩。

**修好之后：4.23 fps，有画面，但 CPU 异常峰值 85,487 次/秒。**

## ★ 最大的一次单点提速（93 号，10-30 19:30）

## 10-30 21:02：爆发窗口不是创建对象（104 号）

```
[perf] PREP3 vert=2.9 tex=1470…7964 shader=0.0 ms    creados tex=0 rt=0 pip=0
```

**`tex` 的爆发和对象创建无关 → 是"读被监视的 guest 内存"。**

**根因回到第二章那个硬约束：**

```
svcSetProcessMemoryPermission -> 0xD401
```

Switch 不能把页设成"只读+监视"，SDK 只能**取消映射**来代替。
于是：**读被监视页的每 4 个字节 = 一次 CPU 异常。**上传一张纹理要读几 MB。

## 10-30 21:13 / 21:27：两次失败（105、106）

| 版本 | 做法 | 结果 |
|---|---|---|
| v11 | 纹理上传前整段解除监视 | `tex` 7964→26 ms，但 `vert` 14.6→431 ms，**fps 12.02→5.63** |
| v13 | 只解已保护页 + 连续段 | 仍 `vert=442 ms`，**fps 5.52** |

**根因**：每次上传都要扫全表 + 拿全局锁 → 顶点路径被串行化。

**结论：这条"按需解锁"的路走不通。**

`Cod6GraphicsSystem::CreateCommandProcessor()` 返回我们自己的处理器。
**当时 5.35 fps，我一度以为"native 模式慢一半" —— 后来你指出是没超频，我收回这个结论。**

## 顶点读取：连续失败四次（这条要记住）

| 版本 | 做法 | 结果 |
|---|---|---|
| 18 | `TranslatePhysical(addr)` | 读全 0 |
| 19 | 去掉 `<<2` | 读全 0 |
| **20** | `TranslateVirtual(addr<<2)` + 裸指针 | **崩溃黑屏**：`Unhandled guest access violation: read of guest 0x80400002` |
| 24 | 加 `& 0x1FFFFFFF`（照 MW1 参考项目） | 不再崩，但仍读 0 |

**最终真相（查 Xenia 的 `xe_gpu_vertex_fetch_t` 定义）：**

```c
union xe_gpu_vertex_fetch_t {
    FetchConstantType type : 2;
    uint32_t address : 30;      // dword 单位
    Endian endian : 2;
    uint32_t size : 24;
};   // 一共 8 字节
```

**顶点格式/stride/偏移**根本不在 fetch 常量里** —— 所以手工解析 guest 内存这条路**天生走不通**。

**正确做法（已实现）：** 在 SDK 的 `IssueDraw` 里、`PrimitiveProcessor::Process()` 之后取
`primitive_processing_result`（里面是**已经解码好的**数据）。新增
`sdk/include/rex/graphics/vulkan/nativo_hooks.h`。

## ★ 120 号（10-31 00:08）：小绘制的真实形态

```
NATIVO DIBUJO: pequenos=46000  con_handle=46000
    (ultimo: n=1  v=1  tipo=0  prim=1  handle=0xFFFFFFFFFFFFFFFF)
```

**发现：**

1. `tipo=0` = **没有索引缓冲** → 走 `CmdVkDraw`，不是 `CmdVkDrawIndexed`
2. **每个 UI 四边形只有 1 个顶点** → 顶点着色器里展开成方块
3. `handle = 0xFFFF...FFFF` = 无效

**这解释了之前所有困惑**：为什么索引不指向顶点缓冲、为什么 16 个 fetch 槽位全是 0。
