## 一、文档里的四件事（按必须的顺序）

### 1. 直接调用（必须先做，否则 LTO 白费）

**问题**：GCC 下 `DEFINE_REX_FUNC` 把每个游戏函数 `sub_X` 变成 `__imp__sub_X` 的**弱别名**。
弱别名的用途是让 hook（`REX_HOOK_RAW`）在链接时替换掉它。但**编译器永远无法内联一个弱别名**
—— 同一文件里不行，开了 LTO 也不行。所以生成的游戏代码几乎无法被内联优化。

**做法**：`tools/llamadas_directas.py` 把没有 hook 的 `sub_X(ctx, base);` 改写成
`__imp__sub_X(ctx, base);` —— 同一个函数，但可以内联了。

- 他们的数字：**83,077 个调用里改掉了 79,612 个**（96%）。
- 注意：**每次重新生成代码后都要重跑**这个工具。
- 改完后要用 `nm` 核对：编译产物里定义的 `sub_` 必须都在"已 hook"名单里。

### 2. LTO

只在 Switch 构建里用：`-flto -fno-fat-lto-objects`，链接 `-flto=2 -flto-partition=balanced`。
**链接时内存占用很大**，LTO 任务数要压低。

### 3. PGO（GCC 16 + Horizon）

两次构建，同一个 build 目录、同一份生成代码、同一份源码：

1. **录制版**：`-fprofile-generate`，LTO 关。他们做出来 82.7 MB 的 NRO + 16 MB 计数器内存，构建 66 分钟。
   - GCC 会把计数器文件路径写进程序 → 用 `--wrap=fopen` 改到 SD 卡目录；
   - 后台线程每 3 分钟 `__gcov_dump` + `__gcov_reset` 保存一次，崩溃不丢；
   - 要**尽量多玩**（菜单、关卡、视频、各种模式）才准。
2. **优化版**：`-fprofile-use=<dir> -fprofile-partial-training`，LTO 开。

**四个坑（每个都烧掉一次构建）**：

| 坑 | 现象 | 解决 |
|---|---|---|
| 缺 `-fno-profile-values` | 录制版在 `main` 之前就崩（`mrs tpidr_el0` 在 Horizon 上恒为 0） | 加上这个选项；检查程序里没有 `__gcov_indirect_call_profiler` |
| 缺 `-fprofile-correction` | 多线程计数器变负数，GCC 当成坏 profile（他们报 49 个错） | 加上 |
| 两次构建之间重生成代码 | profile 对不上 | 不要动源码/生成代码 |
| 路径不一致 | 文件名对不上 | `-fprofile-prefix-path` 要用 Windows 反斜杠写法 |

### 4. 函数排序

按 profile 的热度给函数排序，让热函数挤在相邻地址上（减少 TLB/页缺失）。
**验收**：`nm nfsmw | grep " _start$"` 必须输出 `0000000000000000`，否则 NRO 起不来。

## 二、这些带来的收益（他们实测）

| 步骤 | 做了什么 | 赛道 fps |
|---|---|---|
| 5 | 降低每绘制 CPU 成本 + GPU 460.8 MHz | 30.3 |
| **6** | **直接调用 + LTO + PGO + 函数排序** | **~34** |
| 7 | 热函数改写成原生代码 | 35.4 |

所以第 6 步整套 = **+12% 左右**。而且这 12% 是加在**游戏自身 CPU 时间**上的。

## 四、结论：能做，但现在收益有限

1. **能复用他们的工具**：`llamadas_directas.py` 支持 `--gen` 指定生成目录，我们的生成代码在
   `generated/default`，改一下路径参数就能跑。
2. **收益估算**：他们整套 +12%；只看"直接调用 + LTO"大概 **+5~10% 的游戏 CPU 时间**。
   我们主菜单是 **GPU/呈现受限**（CPU 只用 1 个核），所以这 5~10% 落在"游戏自身 16 ms/帧"上
   → 每帧省 1~2 ms → 大约 **+0.3~0.5 fps**。**几乎看不出来。**
3. **关卡内不一样**：那里是每绘制成本主导（0.42 ms × 5142），编译器层的收益同样被淹没。
4. **所以顺序应该是**：先把渲染器做出来（参考项目的第 2~4 步），等 CPU 真正成为瓶颈
   （他们的第 5 步之后）再做编译器层（第 6 步）。**他们也是这个顺序。**

## 五、如果现在就想要这个 +5~10%

最小的动作（半天内可完成）：

1. 把 `llamadas_directas.py` 拷过来，路径参数指向我们的 `generated/default`，
   hook 名单用我们自己的 15 个函数；
2. 跑一遍，确认 `sub_X(ctx` 从 55,205 掉到接近 0（只留 hook 的那些）；
3. 加 `-flto -fno-fat-lto-objects` + `-flto=2 -flto-partition=balanced`，重新构建
   （链接会明显变慢，内存要够）；
4. 用 `nm` 确认 `_start` 在 0，然后真机测一次。

**风险**：LTO 会让构建时间从 22 秒变成几分钟到十几分钟；链接可能因为内存不足失败。
**收益**：主菜单几乎看不到；关卡内也不解决根本问题（每绘制 0.42 ms 是渲染层的事）。
