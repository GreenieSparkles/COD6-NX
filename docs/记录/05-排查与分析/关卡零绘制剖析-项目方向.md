## 一、测量结果

配置：`cod6_saltar_dibujos = true`（一次绘制都不做）+ v88（我们的绘制关闭）
场景：进关卡，实际可操作（角色移动、射击都正常，只是慢）

| 指标 | 数值 |
|---|---|
| 帧率（关卡内） | **14.3 ~ 15.0 fps** |
| 每帧时间 | **53 ~ 70 ms** |
| 绘制数/帧 | **0** |
| CPU 总占用 | 166 ~ 172%（== 1.7 核，满 400%） |
| 客机读缺页 | 0（没有绘制就没有缺页） |

用户主观感受："15-20 fps，能控制角色、能射击，一切都正常，就是慢" —— **完全对上**。

## 二、那 1.7 个核花在哪（同一窗口的线程占用）

| 线程 | CPU |
|---|---|
| XThread（客机线程） | 24.7% |
| **GPU Commands**（命令处理线程，即使全部跳过绘制） | **24.7%** |
| Backend | 20.1% |
| Worker1 / Worker0 / Worker2 | 18.4 / 17.3 / 15.7% |
| Main XThread（客机主线程） | 17.0% |
| Database | 10.0% |
| XMA Decoder | 9.2% |

**关键观察**：

1. **没有单一热点**——时间摊在约十个线程上（游戏逻辑 + 命令流解析 + worker 线程）；
2. **只解析命令流就要 0.25 个核**：5,142 次绘制的 PM4 包即使全部跳过，GPU Commands 线程仍占 24.7%；
3. 客机自己的线程合计约 60%，这就是"游戏自身代码"的成本。

## 三、结论（这就是之前一直想要的那个答案）

| 目标 | 判定 | 依据 |
|---|---|---|
| **菜单/界面 40 fps** | ✅ **可达** | 零绘制 38~44 fps（177 号），且我们已能画出正确几何，只差纹理采样时机 |
| **关卡内 30 fps** | ❌ **不可达**（不是渲染器的问题） | 零绘制只有 14~15 fps；即使渲染器完美、绘制零成本，也到不了 30 |

参考项目对同一堵墙的做法（他们第 7 步）：把最热的游戏函数改写成原生 C++。但那是在
**他们已经有 30+ fps** 之后做的（34 → 35.4）。我们的关卡连 15 fps 都不到，且热点是分散的，
不是"改几个函数就翻倍"的形态。

## 四、所以项目的合理定位

**"菜单与界面由我们自己的渲染器画出、约 40 fps 可玩"** —— 这是真实可达的目标，
而且离得很近（只差纹理采样时机这一块工程）。

**"战役关卡流畅游玩"** —— 需要：完整自研渲染器（月级）+ 游戏函数原生重写（月级）+
命令流解析优化，而且不保证到 30 fps。这个投入产出比必须由项目所有者决定。

## 五、下一步（建议顺序）

1. **把纹理做完**（5~10 轮）→ 菜单 UI 由我们正确画出 → 达到"菜单 40 fps 可玩"；
2. 停止在关卡上继续投渲染器工作，除非决定走"完整渲染器 + 原生化"的月级路线；
3. 把当前成果固化：交付稳定版、文档、备份。
