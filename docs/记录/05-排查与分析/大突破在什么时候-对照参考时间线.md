# 大突破在什么时候 —— 对照参考项目的实测时间线

写于第 166 轮。参考项目文档：`native-renderer.md`、`performance-history.md`、
`porting-another-game.md`（在 `/opt/switch/nfsmw-ref/docs/`，也可从仓库读）。

---

## 一、参考项目的 8 步（全是真机、标准频率、同一条赛道）

| 步骤 | 做了什么 | 结果 |
|---|---|---|
| 1 | 用 SDK 自带的 GPU 模拟 | **1~3 fps** |
| 2 | **自研渲染器第一版**（先在 PC 上开发） | **16.1 fps** |
| 3 | GPU 工作量从 60 ms 砍到 33 ms | 26.0 fps |
| 4 | 修帧节奏（渲染出的每一帧都真的上屏） | — |
| 5 | 降低每绘制 CPU 成本 + GPU 460.8 MHz | 30.3 fps |
| 6 | 直接调用、LTO、PGO、函数排序 | ~34 fps |
| 7 | 把游戏最热的函数改写成原生代码 | 35.4 fps |
| 8 | 发布版 | 32~35 fps |

他们自己写的关键句：

> "It was developed on the PC first. **In two days** it drew videos, menus, the HUD and full
> races with the rear-view mirror, reflections and shadows, at **1.5-1.8 µs of CPU per draw**."

> "The limit was far below 30 FPS, so the decision was to stop imitating the GPU and draw the
> game's frames with Vulkan directly."

这就是"大突破"的定义：**从 1~3 fps 跳到 16 fps 的那一步，靠的不是调参数，是把整个绘制层换掉。**

## 二、我们在哪儿

对照他们的步骤：

| 他们的步骤 | 我们的状态 |
|---|---|
| 1 模拟 GPU | ✅ 就是现在：主菜单 16 fps，关卡内 0.5 fps |
| 2 自研渲染器 | 🟡 **刚开始**：管线 + 提交 + 能在最终画面上画几何体（第 166 轮，屏幕变红那次） |
| 3 GPU 工作量 | ⬜ 未开始 |
| 4~8 | ⬜ 未开始 |

也就是说：**我们刚刚走到"他们的第 2 步的开头"**——"hello triangle" 级别的证明已经拿到，
剩下的是把这个三角形变成"能画游戏真实内容"的渲染器。

## 三、"大突破"的判据（可测量，不靠感觉）

    现在：主菜单 16 fps；关卡内 0.5 fps（5142 绘制/帧 × 0.42 ms）
    突破点：主菜单由我们渲染器绘制 → 预期 40~60 fps
    第二跳：关卡内由我们渲染器绘制 → 预期 15~25 fps（参考项目第一版是 16.1 fps）

参考项目给了一个很有用的对照：他们的**菜单约 800 次绘制，模拟层只有 3.3 fps**；
我们菜单只有 82 次绘制却有 16 fps，说明我们的"每次绘制成本"比他们更高（他们 80 µs/绘制，
我们 420 µs/绘制）。**换成自己的渲染器后，这个数字会从 420 µs 掉到 2 µs 量级**，
这就是那一跳的来源。

## 四、从现在到第一整帧，需要的四件事（按他们的顺序）

他们的每绘制流程（`native-renderer.md` 的 "Each draw"）：

1. 从 GPU 设置算出需要哪条管线（我们有：SDK 已经算好，`pipeline_cache_`）
2. 找纹理（两级缓存 + 指纹）
3. **把顶点和索引拷进上传缓冲，同时把字节序从 360 的大端换成 Switch 的小端**
4. 把变化的着色器常量写进 dynamic uniform buffer
5. 绑定变化的部分并记录绘制

我们现在缺的是 3、4 和"真实的 1、2"。具体拆成：

| # | 工作 | 产出 | 量级 |
|---|---|---|---|
| A | **顶点解码**：读 fetch 常量 + 顶点属性格式，把位置读出来 | 日志里出现正确的屏幕坐标 | 几天（v71 这个包就是拿格式数据） |
| B | **用我们的管线画真实四边形**（先不打纹理，纯色） | 屏幕上位置正确的色块 = 数据通路验证 | 几天 |
| C | **纹理**：从 guest 内存取纹理、去 tile、上传、采样 | UI 字形/图标出现在正确位置 | 1~2 周 |
| D | **渲染目标/EDRAM 替代 + 帧节奏** | 完整一帧由我们画 | 数周 |

参考项目在 C/D 上花了大部分时间（他们的 `nfsmw_nativo_destinos.cpp` 328 KB、
`nfsmw_nativo_dibujos.cpp` 687 KB），并且第 3~8 步又花了好几个月。

## 五、诚实的结论

- **"什么时候有大突破"**：第一次帧率跳变出现在 **B 完成之后**（我们自己的渲染器画出位置正确的
  UI 内容），不是现在。以参考项目的量级，B 是"几天"级，C 是"两周"级，D 是"数周"级。
- **不会有"某一天突然从 0.5 变成 30 fps"的魔法**：他们的曲线是 16.1 → 26.0 → 30.3 → 34 → 35.4，
  每一步都是具体的工程改动。
- **唯一能保证的是**：不换渲染层，关卡内永远是 0.5 fps（他们文档原话：两天只优化模拟层，
  赛道从 2.0 到 3.7 fps）。
