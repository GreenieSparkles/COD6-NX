## 一、参考资料的主线，就一句话

> **不要优化模拟层。自己读 PM4 ring，用 Vulkan 直接画；再把游戏自身代码变快。**

他们的原话（`native-renderer.md`）：两天在模拟层上做裁剪（strips、关 pass、降阴影频率）只到 3.7 fps，
所以放弃优化，换原生渲染器。台阶（`performance-history.md`）：

| 步骤 | 比赛场景 fps |
|---|---|
| 1 模拟 GPU | 1–3 |
| 2 第一版原生渲染器 | **16.1** |
| 3 GPU 工作 60 → 33 ms（ZCULL、resolve 不拷贝、动态常量缓冲…） | 26.0 |
| 4 帧节奏（一半帧被扔掉） | 全部帧上屏 |
| 5 CPU/绘制成本 + 性能配置（GPU 460.8 MHz） | 30.3 |
| 6 **direct calls + LTO + PGO + 函数排序** | **~34** |
| 7 最热游戏函数原生替换 | 35.4 |

## 二、我们在这条线的哪一格（实测，不是估计）

| 指标 | 我们 | 参考项目 |
|---|---|---|
| 主菜单 | 13.18 fps，82.7 绘制/帧，≈0.7 ms/绘制 | 菜单 800 绘制/帧，模拟 3.3 fps → 原生后 ~14 fps |
| 关卡内 | 0.5 fps，5,142 绘制/帧，**0.42 ms/绘制** | 比赛 2.0–2.2 fps |
| **一像素不画（菜单形状）** | **61.74 fps / 16.2 ms**（118 号，0 绘制，600/600 都是 ≤8 顶点） | 标题画面 58.6 fps |
| **一像素不画（关卡形状）** | **13.70 fps / 73.0 ms**（128 号，0 绘制，1,141 绘制/帧） | 比赛 **2.1 fps**（去掉全部 GPU 工作） |
| 原生渲染器 | 只有测试方块；但"提交归我们"已验证（42,000 次 vkCmdDraw） | **1.5–1.8 µs/绘制** |
| 构建层 | 寄存器本地化**已开**；direct calls / LTO / PGO / 函数排序**全没有** | 全有 |

### 两个最重要的推论

1. **主菜单**：天花板 61.7 fps，而现在是 13 fps → 这 59 ms/帧就是模拟层的每绘制成本。
   换原生渲染器（哪怕只做到 10 µs/绘制）菜单就能进 40–60 fps。**菜单这一仗是纯渲染器问题。**
2. **关卡内**：零绘制时只有 13.7 fps（73 ms/帧），这是**游戏自身代码**的开销。
   就算渲染器做到 2 µs/绘制（5,142 × 2 µs ≈ 10 ms），也只有 73 + 10 = 83 ms ≈ **12 fps**。
   → **关卡内光换渲染器不够，必须同时把游戏自己的代码变快。**这正是他们第 6、7 步。

## 三、他们验证过、我们还没做的（按性价比排序）

### A. 构建层 —— 不碰任何逻辑，风险最低

| 项 | 他们的数字 | 我们的现状（已核对） |
|---|---|---|
| **direct calls**（`sub_X(ctx,...)` → `__imp__sub_X(ctx,...)`，只对没被 hook 的函数） | 改写 **79,612 / 83,077** 次调用；弱别名让 GCC 永远不能内联，**这是 LTO 能生效的前提** | 生成代码里 **55,205 次 `sub_X(ctx`，0 次 `__imp__sub_X(ctx`** → 一次都没做 |
| **LTO** `-flto -fno-fat-lto-objects`，链接 `-flto=2 -flto-partition=balanced` | 与下面两项一起：30.3 → **~34 fps** | `out/nx/build.ninja` 里 **0 处 `-flto`** |
| **PGO**（两遍构建 + `.gcda` 重定向到 SD + 每 3 分钟 dump）。坑：`-fno-profile-values`（Horizon 上 tpidr_el0 恒 0）、`-fprofile-correction`（多线程计数为负）、两遍之间不能改代码 | 同上 | 没做 |
| **函数排序**（`.ld`；坑：`.text` 第一行必须是 `KEEP(*(.crt0))`，且每次校验 `_start` 在 0） | 同上 | 没做 |
| **rexcrt**（`memmove` 950 处、`strncpy` 换原生） | 有收益 | 没做 |
| 寄存器本地化 `cr/xer/ctr/non_volatile_as_local` | 去掉 172,403 次 `ctx.xer`、32,637 次 `ctx.ctr`、23,857 次 `__savegprlr_*`；他们主线程 14% 花在两个 save/restore 上 | **已开** ✅（`/opt/switch/cod6-ng/overrides.toml`） |

我们编译器是 devkitA64 **GCC 15.2.0**，LTO/PGO 可用（他们用 GCC 16）。

### B. 结构性：原生渲染器接管真实绘制（他们的 1.5–1.8 µs/绘制，我们是 420 µs/绘制，差 250 倍）

按他们的实现顺序，我们还缺：
1. **顶点/索引读取**（他们：顶点拷贝线程，端序转换，去重）——我们的卡点（N3-1）
2. **纹理 untiling + 指纹缓存**（16 字节一组 NEON；PC 上从 66 µs → 4.2 µs/绘制；512 MB 上限、16 MB 大块分配）
3. **管线缓存 + 启动预热**（他们 113/113 管线 0.3 s 就绪；NVK 冷建一个 59 ms）
4. **渲染目标替代 EDRAM**、resolve 不拷贝、只把 64×64 曝光图写回游戏内存（省 98%）
5. **三槽并行**（三份命令缓冲 + fence + 上传/读回缓冲，CPU 录下一帧时 GPU 画当前帧）
6. 他们说**必须**有的两件"让游戏对上号"的东西：shader 归属识别（D3D 改过 microcode）、
   以及把 `WAIT_REG_MEM` 变成真写 `SCRATCH`（否则一秒内死机）

### C. 游戏侧 CPU —— 关卡内的真正瓶颈（73 ms/帧）

- **最热游戏函数原生替换**（他们：材质参数 2–4%、特效参数 5%、可见性 82,000 次/秒、
  每绘制矩阵 595→394 指令、把每绘制 14 个包的 D3D 状态打包成 1 个 marker），每个都带 guard
- **游戏自己的 busy wait 换成真等待**（我们的 `Cinematic` 线程烧 46.3% 主菜单 / 76.8% 关卡内，同一类问题）
- **页故障路径**（我们 167,405 次/秒读异常；他们 `platform-notes.md` 里也是主项）

### D. GPU 侧

- **ZCULL** 在 NVK 里打开（他们省 ~2 ms/场景）→ 我们的 NVK 是预编译 `libvulkan.a`，要重编 Mesa
- 着色器常量走 dynamic uniform buffer、去掉 texture size 查询
- 着色器**预编译库**（XenosRecomp→HLSL→DXC）：我们 `PREP3 shader=0.0 ms`，**暂时不急**

## 五、建议的执行顺序

| 轮次 | 做什么 | 预期 | 风险 |
|---|---|---|---|
| 152（已出包） | `readback_memexport = false` | 主菜单去掉 16.4 s/46.8 s 的 GPU 同步 | 低（cvar 可回退） |
| **153** | **A 的头两项：direct calls + LTO** | 游戏自身代码 +10~15%（他们 30.3→34 的共同来源） | 中：LTO 链接吃内存、首次全量重建久；机械可回滚 |
| 154 | PGO + 函数排序（先在卡上跑一遍采 profile） | 同上再加一点 | 中高：两遍构建不能改代码，坑多 |
| 155+ | **B 主线：原生渲染器**（N3-1 顶点读取 → 纹理 untiling → 管线缓存 → RT/resolve → 三槽） | 菜单 40~60 fps；关卡内的绘制成本 2160 ms → ~10 ms | 高（大工程），但这是唯一进关卡的路 |
| 并行 | C：D3D 状态打包成 marker、可见性等最热函数、busy wait | 关卡内 73 ms 往下压 | 中 |
| 并行 | PC 版修好（他们第 1 步："所有翻译问题在 PC 上更好查"） | 调试基础设施 | 低 |

**一句话**：菜单靠渲染器，关卡靠"渲染器 + 游戏侧 CPU"，而我们现在最便宜的一块肉是
**构建层的 direct calls + LTO（一次机械改动）**，最贵但必须做的是**原生渲染器接管真实绘制**。

| 层 | 现在是什么 | 效率 | 该变成什么 |
|---|---|---|---|
| **游戏 CPU 代码**（PowerPC） | ReXGlue **AOT 翻译成 C++**（61 个文件、63 MB、**18,848 个函数**），再由 devkitA64 **GCC 15.2.0** 编译成 ARM64。运行时**没有 JIT、没有解释器** | 是"真编译器"，但优化开关没开：**55,205 次调用走弱别名**（GCC 无法内联）、**无 LTO / PGO / 函数排序** | 开上那几项（参考项目 30.3 → ~34 fps） |
| **Shader**（Xenos microcode） | **运行时翻译**成 SPIR-V（`spirv_translator_*` + glslang），另有 `interpreter.cpp` 兜底 | 我们的 `PREP3 shader=0.0 ms` → 不在热点上 | 预编译进 shader library（暂不急） |
| **GPU 命令**（PM4 ring） | **运行时模拟**：ReXGlue 的 `xenos` 插件（EDRAM 模拟 + 状态跟踪 + 每绘制 ~0.42–0.7 ms） | **这才是"不高效"的根源** | 自己的渲染器读 ring 直接发 Vulkan（1.5–1.8 µs/绘制） |

## API：只能是 Vulkan（NVK），没有第二选项

- **OpenGL**：Horizon 上根本没有 GL 驱动，不存在。
- **D3D**：是**客机内部**的东西。游戏自己跑它的 D3D9（Xbox 360 的 API），照旧往 PM4 ring 写命令；
  我们拦截的是 ring，不是替换它的 D3D。PC 上才有 D3D12 后端（`sdk/src/graphics/d3d12/`），Switch 用不上。
- **Vulkan**：我们已经在用。链接的是
  `/opt/switch/mesa-sdk/opt/devkitpro/portlibs/switch/lib/libvulkan.a`（92 MB，2026-10-28 构建），
  来源 `/opt/switch/dl/mesa-switch-main` —— **未打补丁的 NVK**。
- **deko3d**：devkitPro 里有 `libdeko3d.a`（Switch 原生、更薄、每绘制更省 CPU）。
  但换 deko3d = 整个后端重写，而参考项目用 **Vulkan/NVK** 就做到了 30–35 fps → 不值得换。
- **参考项目的 NVK 补丁**（`/opt/switch/nfsmw-ref/mesa/mesa-switch-nfsmw.patch`，138 KB，**35 个文件**，
  含 ZCULL 相关 85 处、`nvk_cmd_draw.c` / `nvk_descriptor_table.c` / `nvk_mem_arena.c` 等每绘制路径）
  **我们没有**。干跑试过：**46 处冲突**（他们的 Mesa 版本和我们的不同），要逐块移植才用得
  —— 这是"驱动层"的独立收益点，排在渲染器之后。

## "有可玩效率"的阶梯（数字都从实测推）

| 里程碑 | 主菜单 | 关卡内 | 依赖 |
|---|---|---|---|
| 现在 | 13 fps | 0.5 fps | — |
| 152 版（memexport 读回关掉） | 14–16 | ~0.6 | 已出包 |
| + 构建层（direct calls/LTO/PGO/排序） | 16–18 | ~0.7（天花板 13.7 → ~15） | 游戏侧代码 +10–15% |
| **+ 原生渲染器接管真实绘制** | **40–60（菜单可玩）** | ~12 | 每绘制 420 µs → 2–5 µs |
| + 游戏侧 CPU（热函数、busy wait、页故障）+ NVK 补丁 | 50+ | **25–30（关卡可玩）** | 73 ms → 25–30 ms |

**所以"什么时候可玩"有两个里程碑**：
1. **菜单可玩** = 原生渲染器接管真实绘制完成（这是最近的、最值得先拿下的一仗）；
2. **关卡可玩** = 那之后再叠加游戏侧 CPU 与驱动层的工作。

换 API（追 D3D/OpenGL）不会带来这一步；**Vulkan 已经是终点，缺的是"不再模拟 GPU"和"把游戏自己的码变快"**。

# 七、COD4/COD5 这条线：同族引擎已经在这台机器上跑到 60 fps

写于第 154 轮之后，核对本机资料后补充。**结论：参考价值不是"有"，而是一份现成蓝图。**

## 1. 真正的宝藏不是那些 md，是本机这三样

| 位置 | 是什么 | 为什么值钱 |
|---|---|---|
| `/opt/switch/nfsmw-ref/` | **参考项目的完整源码**（不只是文档） | 原生渲染器本体：`nfsmw_nativo_dibujos.cpp` 672 KB、`nfsmw_nativo_destinos.cpp` 324 KB、`nfsmw_nativo_sistema.cpp` 236 KB，另有 `shaders/` 工具、`mesa/` 补丁、`pgo/` 配置 |
| `D:\主机掌机\NSLITE\COD4CN_v1.31_发布\整合包\switch\codmw\` | **同引擎族的 COD4 实机可玩包** | 掌机 **1280×720 / 60 fps / 全特效 / LOD 0 / 16× 各向异性**；`codmw.nro` 40.9 MB + **`codmw_shaders.nfsp` 75.1 MB 预编译着色器库** + `codmw.toml` |
| `codmw.toml`（60 个键） | 一份"哪些开关有用"的清单 | 见下 |

**关键事实：我们的 SDK 就是他们那套 fork。**
`diff` 两棵 SDK 的文件清单：`nfsmw-ref/sdk` 比 `cod6-ng/sdk` **多 0 个文件**（同一套文件，我们在上面改过 22 个）。
所以缺的不是 SDK，是 app 层的渲染器。

**另一个反直觉的事实：他们的原生渲染器不是继承 SDK 的 command processor。**
`nfsmw_nativo_*.cpp` 里没有任何 `rex::graphics::vulkan::` 调用，只 include 了自己的头 + `sdk/src/core/threading_switch.h`
——他们自己管 Mesa/Vulkan，从 SDK 只拿线程工具。
我们现在 N3 路线（子类化 `VulkanCommandProcessor` + 钩 `IssueDraw`）能验证概念，但要做性能就得换成他们那种"独立渲染器"结构。

## 2. `codmw.toml` 里可以直接抄的开关

| 开关 | 作用 | 我们有吗 |
|---|---|---|
| `nfsmw_renderizador = "nativo"` | 用原生渲染器而不是模拟层 | 只有 `cod6_renderizador` 的壳 |
| `codmw_dibujos_hilo = true` / `codmw_grabador_hilo = true` | 绘制录制放在独立线程 | 没有（单线程） |
| `codmw_prioridad_hilos = "Main XThread=0x2C,..."` | 线程优先级 | 没做 |
| `codmw_switch_gpu_mhz = 460` + `codmw_switch_ram_1600` | 主动申请性能配置（不是超频） | 没有（我们现在是被 sys-clk 超到 768） |
| `codmw_cache_vertices_mb = 128` / `codmw_texturas_pool_mb_inicial = 256` | 顶点缓存 / 纹理池 | 没有 |
| `codmw_skinning_gpu` / `codmw_instancias` | GPU 蒙皮 / 实例化 | 没有 |
| `codmw_saltar_prepaso` / `codmw_juego_sin_prepaso` | 跳过一遍渲染 | 没有 |
| `codmw_dvars = "r_lodScaleRigid 0; r_dof_enable 0; ..."` | **直接改游戏自己的 dvar 来降负载** | 没有（这条可能最便宜、最有效） |
| `codmw_texturas_verificar = 0` | 关掉纹理校验 | 没有 |
| `codmw_shaders.nfsp` | 预编译着色器库 | 没有（我们运行时翻译） |

→ 这些是"开关级"的活，便宜、可回滚，可以在渲染器之前先试。

## 3. 能复用多少

## 4. 时间：三个里程碑，诚实分档

| 里程碑 | 内容 | 依据 |
|---|---|---|
| **菜单流畅 40–60 fps** | 原生渲染器接管真实绘制 | 本项目早先自估"2~3 周连续作业"；现在有源码 + COD4 配置，风险显著降低 |
| **关卡内 25–30 fps** | 渲染器 + 游戏侧 CPU（构建层、原生热函数、busy wait）+ GPU 调整 | 参考项目 16.1 → 35.4 走完 8 步约一个季度（1~2 人） |
| **全特效 60 fps** | 上面全部 + Mesa 补丁 + PGO + 函数排序 + 原生替换 + dvar 精简 | COD4 实机已经做到，但那是完整一整套 |

不给日历日期，但依赖关系是硬的：**菜单卡在"渲染器接管"，关卡卡在"渲染器 + 游戏侧 CPU"。**
换 API（D3D/OpenGL）不会带来任何一步；Vulkan/NVK 已经是终点。
