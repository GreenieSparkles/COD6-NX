# 〇、定案（第 152 轮，用 150 号日志 / 版本 57 实测）

版本 57 把「发出绘制之后」那段切开跑了一次，日志 `新建文件夹 (150)`，结果**不是** memexport 整块失效：

    这次运行：446 帧、9.53 fps、105 ms/帧、102.2 次绘制/帧
    [perf] COLA_LENTO 共 401 条，合计 21,120 ms（占整机墙上时间 46.8 s 的 45%）

| 分组 | 条数 | 合计 | 平均 | 时间落在哪 |
|---|---|---|---|---|
| `memexp=1` | 175 | **16,405 ms** | **93.7 ms** | **99% 在 `cola` 段** |
| `memexp=0` | 226 | 4,714 ms | 20.9 ms | **100% 在「发出绘制之前」** |

`cola` 段就是 `IssueDraw_MemexportReadbackFastPath/FullPath` ——
而 fast 路径在「上一槽的提交还没完成」时会退回
`IssueDraw_MemexportReadbackFullPath` → `AwaitAllQueueOperationsCompletion()` = **等整个队列跑完的 GPU 同步**。
一次 94 ms、中位 109 ms，正是等一帧 GPU 的量级。

**所以主因是：memexport 的 CPU 读回（GPU→CPU 同步）。** 它默认是开的
（`readback_memexport = true`，`sdk/src/graphics/command_processor.cpp:67`），
toml 里从来没关过。

**而且我上一轮最强的那个假设是错的**：`inval_todo=0` 出现在全部 401 条里，`media_inval=0.00`
→ `RangeWrittenByGpu(0, 512 MB)` 那条分支一次都没跑到。整块失效不是元凶，可以划掉。

版本 58 的处理：
1. `cod6.toml` 里加 `readback_memexport = false`（**这一条就是主修复**，预期 9.5 → ~14 fps 量级）；
2. 剩下的 4,714 ms（每次 21 ms、全部在绘制之前）按 `vfetch` / `barreras` 再拆一刀，
   看是不是顶点缓冲驻留（`RequestRange` → 页监视取消映射）造成的。

方向对，但那三小项本身是不可信的：

**假数 1：`fase5` 写在 `return` 之后，永不执行**

```cpp
if (!UpdateBindings(vertex_shader, pixel_shader)) {
    return draw_fail("update_bindings");
  guardiaPerfDraw.fase5 = std::chrono::steady_clock::now();   // ← 死代码
}
```

结果 `f5` 回退成 `f4`，于是 `bindings` 恒为 0，`vfetch_resto` 把 UpdateBindings 一起吞了。
**151 轮（版本 57）已修好**（把赋值挪到 if 之后）。

**假数 2：`vert / tex / resto_prep` 三个括号字段恒为 0.0**

同一行里 `prep=33.3`，括号里三个分量却是 `0.0 / 0.0 / 0.0`，自相矛盾
（PREP3 那一行同时报 `vert=45.1 tex=0.3`）。也就是说这一行括号里的拆分不能用来做判断。

## 二、真正的发现：绘制时间是双峰，钱在极少数几次绘制上

217 个窗口的直方图，几乎每个都长这样（每个窗口 120 次绘制）：

    <0.1ms=114   <0.5ms=3~6   <1ms=0   <5ms=0~1   <20ms=0~1   >=20ms=1~2

全量统计（434 个直方图 = 217 窗口 × 2 份日志去重前）：

| 区间 | 平均每窗口 | 说明 |
|---|---|---|
| <0.1 ms | **111.9 次** | 绝大多数绘制是"免费"的 |
| <0.5 ms | 4.2 次 | |
| <5 ms | 1.9 次 | |
| 5~20 ms | 0.5 次 | |
| **≥20 ms** | **0.89 次** | **吃掉的钱几乎全在这** |

- 69% 的窗口里至少有 1 次 ≥20 ms 的绘制；平均每窗口 0.89 次。
- 窗口跨度 ≈ 1.64 帧（216 窗口 / 354 帧），所以**大约每两帧就有一次约 60 ms 的单次绘制**。
- 反推：24,283 ms（两份日志合计）尾部时间 / 388 次 ≥20 ms 的绘制 ≈ **每次 60 ms 上下**。

也就是说，"resto = 150 ms/窗口"不是 120 次绘制各摊 1.25 ms，而是
**112~115 次几乎为 0，1~2 次各约 60~90 ms**。

## 三、这 150 ms 在代码里的哪一段（唯一可能的区间）

| 区间 | 每次绘制平均 | 证据 |
|---|---|---|
| 管线配好 → 发出 vkCmdDraw（含 UpdateBindings / vfetch / barrier） | **0.01 ms** | `RESTO_SPLIT` 累计 18,840 次 |
| 发出 vkCmdDraw → 函数返回 | **≈ 1.2 ms**（且集中在少数几次） | FASES `resto`（fase2→return）减去上面那段 |

这两段是嵌套关系，所以唯一自洽的解释是：**时间在 vkCmdDraw 之后**。
而 vkCmdDraw 之后这段代码只有三件事（`sdk/src/graphics/vulkan/command_processor.cpp`）：

```cpp
  // 1. memexport 失效登记
  if (!memexport_ranges_.empty()) { … RangeWrittenByGpu(范围) … }
  else if (memexport_writes_possible) {
      shared_memory_->RangeWrittenByGpu(0, SharedMemory::kBufferSize);   // ← 整块 512 MB
  }
  // 2. memexport 读回（vulkan_readback_memexport 默认 false，通常不跑）
  // 3. return true
```

嫌疑最大的是 `RangeWrittenByGpu(0, 512 MB)`：
它走 `MakeRangeValid` → `PhysicalHeap::EnableAccessCallbacks` 遍历全部 131,072 个 4 KB 页，
在 Switch 上页监视只能靠"取消映射"实现（`svcSetProcessMemoryPermission` 返回 0xD401），
一旦命中就是十几万次页表/映射操作的量级 —— 正好是"每两帧一次、一次 60 ms"的形态。

**但这只是最强的假设，不是结论。** 151 轮的版本 57 就是把这个区间切成四段去证实它。

## 四、版本 57 的四个点

    点 A：刚发出绘制（cod6_t_pre_draw → cod6_t_tras_draw）      → media_draw
    点 B：memexport 失效登记之后（→ cod6_t_tras_inval）        → media_inval
    点 C：函数返回（→ cod6_t_fin）                             → media_cola
    点 D：与上一次绘制的间隔                                   → pausa

每 120 次绘制打一行 `[perf] COLA`；每次超过 2 ms 的绘制单独打一行 `[perf] COLA_LENTO`，
带 `vert`（顶点数）、`pitch`（渲染目标宽度）、`memexp`、`inval_todo`（是否整块 512 MB 失效）、
`total/draw/inval/cola/pausa` 的毫秒数和距离上一次绘制的间隔。

## 五、怎么读（一次运行就能定案）

| 日志特征 | 结论 | 下一步 |
|---|---|---|
| `inval_todo=1` 且 `inval` ≈ `total` | 就是整块 512 MB 失效 | 改成按 memexport 范围失效（`memexport_ranges_` 已经算好了） |
| `draw` ≈ `total` | vkCmdDraw 那一刻在等 GPU（提交/fence/管线首次使用） | 查提交边界与 fence 等待 |
| `cola` ≈ `total` | 读回路径 | 查 `vulkan_readback_memexport` / `readback_memexport_fast` |
| `pausa` 大、`total` 大 | 帧边界现象：每帧第一个绘制在等上一帧 | 改提交策略（一帧一次提交 + 不阻塞等待） |
| `memexp=0`、`inval_todo=0` 却还是慢 | 与 memexport 无关 | 看 `vert/pitch` 分组，回到渲染目标/纹理 |

## 六、如果第三、四节的判断成立，值多少钱

尾部合计 24,283 ms（两份日志），占 `en_draw` 的 64%、占墙上时间的 ~39%。
主菜单现在是 13 fps（75.9 ms/帧）；把单次 60 ms 的绘制干掉，
按 82.7 绘制/帧算，主菜单有望进入 **20~40 fps** 区间（GPU 侧天花板是 61.7 fps 的"跳过全部绘制"）。

每次约 60 ms、大约每 1.8 帧一次 → 摊到每帧约 33 ms，正好是 76 ms 帧长里的最大一块。

## 七、旁证：页故障风暴（`rex_perfil.log`，同一次运行）

    第一次报告（0.0 s）：Muestreo de pilas: activo (1 ms)
    10.0 s：juego 14.0 fps | CPU total 165% (400%) | fallos/s: lectura emulada 167405, manejador SDK 84
            | vigilancia: desmapeo (cada lectura falla)
    20.0 s：juego 12.5 fps | CPU total 86%  | fallos/s: lectura emulada 1741
    resumen.txt：fallos_cpu_total = 1,817,819

- `vigilancia: desmapeo (cada lectura falla)` = 页监视只能靠"取消映射"（`svcSetProcessMemoryPermission` 返回 `0xD401`），
  所以**每一次读客体内存都会触发一次异常**。
- 169,000 次/秒的读异常，按每次 2~5 µs 算就是 **0.3~0.8 个核常年在烧**（整机只有 3 个核可用）。
- 这和第三节的嫌疑人是同一条链：`RangeWrittenByGpu(0, 512 MB)` → `MakeRangeValid` →
  `PhysicalHeap::EnableAccessCallbacks` 遍历 131,072 个页 → `rex::memory::Protect` 取消映射 →
  之后每一次读都异常。**这正是"每两帧一次、一次 60 ms"最可能的形态。**

## 八、一个必须记住的混淆项

`switch\cod6-nx\logs\rex\perfil_pilas.flag` 存在时，会开一个 **1 ms 的侵入式栈采样器**：
它每秒几百次 `svcSetThreadActivity(Paused)` + `svcGetThreadContext3` 暂停游戏线程。
历史上所有 12~13 fps 的数字都是在这个采样器开着的情况下测的（`rex_perfil.log` 里写着
`Muestreo de pilas: activo (1 ms)`）。
它同时也是 `COLA_LENTO` 里 `pausa` 字段的干扰源 —— 所以**以后要横向对比帧率时，
要么全开要么全关，别混着比**。
