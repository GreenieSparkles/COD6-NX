   行为完全一样，只是版本字符串不同，不影响任何结论。
2. **上一轮的插桩有 bug（已在 57 修掉）**：
   `guardiaPerfDraw.fase5 = ...` 被写在 `return draw_fail("update_bindings");` 之后，是死代码。
   所以 FASES 行里 `bindings` 恒 0、`vfetch_resto` 把 UpdateBindings 也吞进去了；
   同一行的 `vert/tex/resto_prep` 三个括号字段也恒为 0.0（和 PREP3 行的 `vert=45.1` 自相矛盾）。
   → 之前"已切开 17 ms、剩下 150 ms 未测量"里，那 17 ms 的拆分是不可信的，150 ms 这个量级是对的。

## 149 号日志重新算了一遍（详见 `分析-150毫秒在哪.md`）

    217 个窗口的直方图：平均每窗口 <0.1ms=111.9 次、>=20ms=0.89 次
    → 120 次绘制里 112~115 次几乎免费，真正吃时间是 1~2 次
    → 窗口 ≈ 1.64 帧，所以大约每两帧就有一次约 60 ms 的单次绘制
    RESTO_SPLIT（管线配好→发出绘制）= 0.010 ms/次（累计 18840 次）
    → 时间只能在「发出 vkCmdDraw 之后 → return」这一段
    尾部合计占 en_draw 的 64%、占墙上时间的 ~39%

    vkCmdDraw 之后的代码只有三件事：
        memexport 失效登记（最可疑：else 分支会 RangeWrittenByGpu(0, 512 MB)）
        memexport 读回（vulkan_readback_memexport 默认 false）
        return true
