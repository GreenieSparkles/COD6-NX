## 一、152 号（版本 59）的判读结果

PREP4 每个窗口 120 次绘制，单位 ms/绘制：

    begin    = 0.400     ← BeginSubmission，占单次绘制成本的 93%
    prims    = 0.004     ← 顶点处理几乎免费
    shader   = 0.000
    sampler  = 0.000
    tex      = 0.002
    rt       = 0.014
    页故障   = 15.9 次/窗口（≈0.13 次/绘制，可忽略）

PREP_LENTO：615 次慢绘制、合计 17,195 ms；其中 **500 次的时间全部落在 begin**，
最贵的 8 条（58~66 ms）是 `begin=66.1 / 其余全 0`。

### 两个独立证据指向同一件事

| 来源 | 数字 |
|---|---|
| `[perf] PREP4` 的 begin | 0.40 ms/绘制 × 83 绘制/帧 ≈ **33 ms/帧** |
| `rex_perfil.log` 的 libnx 计数 | `fences esperadas 64 次/s，430.6 ms/s` ≈ **30 ms/帧** |
| CPU 使用率 | 92~145%（3 核可用）→ **CPU 没跑满** |

→ **CPU 在等 GPU。** 主菜单 71.5 ms/帧里约 30~33 ms 是阻塞等 fence。

## 二、这条结论把路线改了一半

上一版我说"顶点处理占 48%"，**那是错的**：`PREP3 vert` 这个标记包含 BeginSubmission，
而它才是贵的。（这就是为什么每轮都要先量再动手。）

于是：

- **direct calls / LTO / PGO（让 CPU 更快）对主菜单几乎没用** —— CPU 现在只用 1 核还闲着两个。
  那一套对**关卡内**仍然有用（关卡内零绘制时 73 ms/帧是游戏自身 CPU）。
- 主菜单的天花板在 GPU 侧：83 绘制/帧、剪刀面积 **39.2 个屏幕**、1 次 resolve、2 个渲染目标、10 次 transfer 绘制。
- 参考项目 `performance-history.md` 第 3 步干的就是这件事：GPU 工作 60 → 33 ms。

## 三、本轮交付（版本 60）

**只复制一个文件：**

    测试\当前\switch\cod6-nx\cod6.nro
      → 卡上 SD:\switch\cod6-nx\cod6.nro

    md5 4b0d8d138524d941dd5760723a29e41e  版本 2026-10-31-60
    toml 不动（沿用 58 版的 readback_memexport = false）

新增测量：在真正阻塞的 `vkWaitForFences` 外面计时 + 记录 GPU 落后多少个提交
（`kMaxFramesInFlight = 3`，每帧 2 个提交）：

    [perf] FENCE bloqueos=N media=X.XX ms max=Y.YY ms | retraso en envios: media=Z max=W

判读：

    media ≈ 30 ms、retraso ≈ 6（=2 帧 × 2 提交）→ GPU 真慢，瓶颈是 GPU 工作量
    retraso 1~2 却阻塞很久 → 不是 GPU 慢，是提交/呈现串行化，改提交策略

## 四、下一步分岔

    A. GPU 真慢 → 砍 GPU 工作（参考项目第 3 步）：
       单 pass 不做 tiling、resolve 不拷贝、ZCULL、**简化运行时翻译出来的片元着色器**
       （UI 过绘制 39 屏的场面，片元着色器长度直接决定成本）
    B. 串行化 → 改提交策略：每帧一次提交、三槽并行、不阻塞等 fence
