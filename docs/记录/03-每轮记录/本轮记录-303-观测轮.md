## 一、本轮开头先做的事：核对交接文档的「优先 1」，结果它被推翻了

交接文档第十章把 **「核对 `ConstantBase` 与 Xenia 的 SET_CONSTANT 编码」** 排在第一位，
怀疑我们自编的基址表把某些类型号的整包寄存器写入丢掉了，导致绘制拿到上一个物体的纹理。

**核对结果：我们的表和 SDK 一模一样，假设 A 不成立。**

SDK 权威实现（`sdk/src/graphics/command_processor.cpp`）：

```cpp
void CommandProcessor::WriteALURangeFromRing(...)       { WriteRegisterRangeFromRing(ring, base + 0x4000, n); }
void CommandProcessor::WriteFetchRangeFromRing(...)     { WriteRegisterRangeFromRing(ring, base + 0x4800, n); }
void CommandProcessor::WriteBoolRangeFromRing(...)      { WriteRegisterRangeFromRing(ring, base + 0x4900, n); }
void CommandProcessor::WriteLoopRangeFromRing(...)      { WriteRegisterRangeFromRing(ring, base + 0x4908, n); }
void CommandProcessor::WriteREGISTERSRangeFromRing(...) { WriteRegisterRangeFromRing(ring, base + 0x2000, n); }
// 索引：uint32_t index = offset_type & 0x7FF;  uint32_t type = (offset_type >> 16) & 0xFF;
```

我们的 `ConstantBase()`（`cod6_native_system_nativo.cpp:1773`）：

```cpp
case 0: return 0x4000;  // ALU
case 1: return 0x4800;  // fetch
case 2: return 0x4900;  // bool
case 3: return 0x4908;  // loop
case 4: return 0x2000;  // registers
default: return UINT32_MAX;
```

→ **基址表一致，索引取法一致（都把 `& 0x7FF` 加在 base 上）。**
`default` 丢弃分支 SDK 也是 `assert + 跳过`，行为等价。

**结论：`SET_CONSTANT` 这条路不是「桌子显示枪贴图」的原因。交接文档第六章的排除表可以加一条：**

| # | 假设 | 排除依据 |
|---|---|---|
| 13 | PM4 `SET_CONSTANT` 常量块映射错（文档方向 A） | 逐行对照 SDK `ExecutePacketType3_SET_CONSTANT` 与 `Write*RangeFromRing`：基址 0x4000/0x4800/0x4900/0x4908/0x2000、索引 `& 0x7FF` 全部一致；`default` 分支 SD​K 也是丢弃 |

## 二、本轮真正的问题：我们没有眼睛

BO2 为什么好，交接文档 5.2 原因 1 说得很准：

> BO2 每改一行渲染器，都能和「正确图像」逐像素对比。**我们没有这个流程 —— 这就是为什么一晚上改 10 个版本，每个都在猜。**

而「桌子显示枪的纹理」这件事，在日志里有两种完全不同的成因，**日志看起来一模一样**：

| 成因 | 存下来的纹理长什么样 |
|---|---|
| a) 纹理内容本身坏了（解码/拷贝/布局算错） | 花屏、错位、邻图残留 |
| b) 纹理是好的，绑错了（绑定/缓存键/时序） | 干净的、完整的、属于别的物体的贴图 |

这两种修法完全不同。所以本轮不猜，先造眼睛。

**源码里其实一直有帧捕获**（`cod6_debug_capture_every` + `cod6_debug_capture_dir`），
而且诊断是编译进来的（`COD6_DIAGNOSTICS` 默认 1），只是**从没在真机上开过**。

## 三、v303 做了什么

版本号 `2026-11-03-303`，`cod6.nro` 41,584,837 B，md5 `DBB2120E866B75CA3AC02679A6DA6527`。
**渲染行为与 v302 完全一致**（所有渲染 cvar 未动），只加观测。

| # | 机制 | 怎么开 | 产出 |
|---|---|---|---|
| 1 | 帧捕获（原有，第一次在真机开） | `cod6_debug_capture_every = 300`<br>`cod6_debug_capture_dir = "sdmc:/switch/cod6-nx/cap"` | `cap/frame_NNNNNN.rgbx`，8 字节头（宽、高）+ R8G8B8X8 行 |
| 2 | **纹理册**（新增） | `cod6_debug_tex_album = 6`<br>`cod6_debug_album_frames = 4` | `cap/tex_fNNNNNN_AAAAAAAA.img`，16 字节头（宽、高、VkFormat、每像素字节），**被捕获那一帧里着色器实际采样的纹理** |
| 3 | **绑定键自查**（新增） | `cod6_native_bind_check = true` | 每个绘制核对「着色器采样的 fetch 槽」是否都在绑定缓存键的掩码里；漏了打 `[bindcheck]`，并在 `[binding-key]` 行给出 `mask_checked` / `mask_missing` |
| 4 | 捕获目录自建 + 失败会报 | 自动 | `[capture] folder ...: ready/failed`、`[capture] CaptureGuestOutput returned nothing for swap N` |

### 为什么第 3 项值得做

绑定缓存键（`native_renderer.cpp` 5352 起）只把 `st.texture_slot_mask` 里的槽的 fetch 字算进键。
如果某个着色器采样的槽不在那个掩码里，**两个贴图不同的绘制就会算出同一个 tb_key，共用一个描述符集** →
后画的物体穿上先画物体的贴图，而且**随着绘制顺序变**，正好是「随机变动」。

这个假设不用看图就能证伪：`mask_missing` 只要一直是 0，这条路就断了；不是 0，就是它。

## 四、从 BO2 挖到的、我们还缺的东西（本轮新增，供下一轮用）

从 `bo2zm.nro` 的字符串里挖出 BO2 自己写的运行期诊断，直接给出它的机制：

```
[native] C3 texture rechecks by write stamps, last 10 s: {} skipped (no stamp since the last check;
   {} of them young, interval 2-4), {} checked anyway (the guard), {} checked (a stamp since);
   {} changed without a stamp (...), their pages now count as always written
```

**三条，我们一条都没有：**

| BO2 的做法 | 我们的现状 |
|---|---|
| **写戳说没变就跳过** | `[texmon] aciertos 0 / fallos 28115` —— 一次没跳过，等于写戳没用 |
| **`the guard`：周期性强制全查一遍** | 文档写着 `first 256 eligible hits and every 64th checked`，有类似的东西，但只在顶点侧 |
| **自愈：变了却没戳 → 那些页从此每帧都算「写过」** | `stamp_mismatch` 时我们只把**那一张纹理**的 `stamp_serial` 清零，**没有把页标成「永久脏」**；同一个 writer 写的下一个纹理仍然会被跳过 |

BO2 还有一条更贴脸的（同样是快路径 + 校验 + 出错就永久关）：

```
[native] C6 texture words reuse: {} reuses checked against the sampler loop, 0 differences: APPLYING (1 in 1,024 still checked)
[native] C6 texture words reuse MISMATCH after {} checks: word {} is {:08X}, the reuse had {:08X}
   (reflection {} / {}; PS n{}): reuse off for this session
```

**「复用上一次绘制的 texture words，抽 1/1024 校验，第一次不符就永久关掉」** ——
我们的 `slot_views` / `tb_cache` 是同一类快路径，但**没有任何校验，也没有出错自关**。
如果 bug 在这条路径上，我们会一直错下去，而 BO2 会在第一次不符时就退化到安全路径。

→ 下一轮的候选（按性价比）：
1. **`mask_missing` 结果**：0 就排除键不全，非 0 就直接修（v303 已在测）。
2. **写戳自愈**：把 `stamp_mismatch` 从「这张纹理不再信任戳」升级为「这段页永久算脏」，照 BO2。
3. **帧+纹理册的结论**：花屏 → 查布局/解码；干净 → 查绑定。
