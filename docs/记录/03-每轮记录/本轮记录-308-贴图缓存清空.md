## 二、真正的根因：贴图缓存被周期性扫光（数据）

`rex_stderr.log` 里两条按 10 秒采样的序列，与 `rex_perfil.log` 的 fps 对齐：

```
  #     fps   created(新上传)   live(存活)
  1       0          9             63
  2    28.9          8            417
  3      30         15             41     ← 掉到 41
  4      30          8              8     ← 掉到 8
  5      30         19             19
  6    35.9        320            320     ← 一次性重建 320 张
  7    12.2        329            338
  8      12          0              0     ← 掉到 0
  9     0.1         19             20     ← 接近冻结 10 秒
 10    43.3         42             42
 11    45.1        484            487     ← 一次性重建 484 张
 12      39        334            338
```

**存活贴图数反复掉到 0，然后一次性重建 320~484 张。**

### 为什么这会导致「贴图逐渐崩坏」

重建 = `im.textures.find(key)` 未命中 → 回到 guest 内存按 `base_page` **重新读一遍并上传**。
但此时那块内存**早已被游戏的贴图流复用了**，读回来的是别人的数据。
于是那个表面就穿上了别的物体（或残留）的贴图，而且**不可逆**：原来那张贴图已经不在了。
贴图流复用越久、清空次数越多，坏得越多 —— 这就是「越玩越糟 / 一切都在逐渐崩溃」，包括
枪口闪光变成一块雷霆方块（特效贴图被清掉后重读到别的东西）。

### 为什么这会导致「跑着跑着卡一下」

一个 10 秒窗口里要解交织 + 上传近 500 张贴图，全部在环线程上做；
再加上 `frame % 60` 的驱逐扫描要遍历整个 `im.textures`。fps 序列里 12.2 / 12 / **0.1** 正好落在这几段。

**所以「卡一下」和「贴图崩坏」是同一个根因。** 你上一个问题我在这里一起回答了。

## 三、清空的来源（代码）

`src/native/nativo/native_textures.cpp`：

```cpp
const uint64_t kEvictFrames = REXCVAR_GET(cod6_native_texture_evict_frames);
if (frame % 60 == 0) {
  ...
  for (auto t = im.textures.begin(); t != im.textures.end();) {
    if (texture.last_used_frame + kEvictFrames < frame) {
      im.Retire(texture.image, texture.memory, std::move(views), texture.last_used_frame);
      t = im.textures.erase(t);
    }
  }
}
```

这个 cvar 就在 `native_textures.cpp` 里 —— 正是交接文档**第七章第 7 条**记录过的那个模块：
「读 toml 时该模块还没注册 cvar，值进了 pending 表且没被补应用 → toml 对该 cvar 的赋值全部无效」。

**若运行时读到 0**，判据变成「只要不是本帧用过就删」→ 每 60 帧扫光整个缓存。
这和测量到的现象逐条吻合，而且能解释「为什么所有历史版本都有」。

同一段代码上还有上一任作者留下的注释，描述的就是这个现象：

> 每 60 帧删一批贴图 → `im.memo.clear()` + `answers_epoch++` → 已录好的命令缓冲若仍指向被释放的
> `VkImageView`，GPU 读到已释放内存，表面就显示别的贴图或垃圾。这符合「一开始好，越久越糟」。

## 四、v308 的改动

1. **代码**：驱逐阈值不允许低于 600 帧，并把**生效值 + cvar 原值**一起打出来：
   `[evict] frame N: X texturas vivas; umbral 600 fotogramas (cvar 0 ...)`
   —— 以后 toml 与运行时再对不上，日志自己会说。
2. **toml**：`cod6_native_texture_evict_frames = 100000000`（等于关闭）。
   理由：日志一直是 `0 freed by the budget`、用 253 MB / 768 MB，预算从来没过，按年龄删是纯损失。
3. **仪表修正**：`[texcheck]` 每 256 次检查打一行成功计数。

### 判断成败（不看画）

```
[evict] frame N: X texturas vivas; umbral ... fotogramas (cvar 100000000 ...)
```

- 存活贴图数**不再掉到 0**、也不再出现「一个窗口新建 300+ 张」的尖峰 → 清空已停
- 若此时贴图崩坏也消失 → **根因确认**
- 若数量平稳却仍在崩坏 → 说明还有别的路径在删贴图，`[evict]` 行会先证明缓存没被清空
