## 一、154 号（版本 60 + toml v61）的结果

    稳态 fps = 13.22（15 个报告），dt = 75.7 ms，绘制/帧 = 80.8
    归一化 fps = 13.22 + 0.100×(82 − 80.8) = 13.34   ← 正好在趋势线上，没有变化

    [perf] FENCE 31 行：media=29.96 ms、retraso=1.69（上一版 28.52 / 1.66）
    "Skipping Vulkan frame presentation" = 0 次

**结论：toml 那一改（vulkan_async_skip_incomplete_frames=false）生效了，但没有任何效果。**
"跳帧 → 帧环被多消费 → 串行化"这个假设**被推翻**。

顺带：这一轮用户最后进了关卡（resumen 显示 5122 绘制/帧、0.50 fps），
所以 resumen.txt 最后的 fps 也不能直接当主菜单结果。

## 二、真正没解释的问题

设计上 `kMaxFramesInFlight = 3`，每帧 2 个提交，CPU 应该等到约 6 个提交之前；
实测等 1.69 个。也就是说**这个环的等效深度不到 1 帧**，CPU 每帧都在等上一帧的 GPU。

## 三、本轮交付（版本 62）

    1. `kMaxFramesInFlight`: 3 → 6
       （sdk/include/rex/graphics/vulkan/command_processor.h）
    2. 新增 [perf] ANILLO，每 60 次呈现一行：
           [perf] ANILLO presentaciones=N cierres=M  cierres/presentacion=X.XX

    cod6.nro  39,815,365 字节  md5 2dba206dd04c7eca3893997eda3b184c   版本 2026-10-31-62
    cod6.toml 不变（v61：readback_memexport=false、async_skip=false）

    实现细节（给下一个会话）：
    - 计数器放在 `IssueSwap` 之前（在 extern "C" 块里声明会导致 C 链接、链接期找不到定义，
      这是本轮踩到的坑：`undefined reference to Cod6ContarPresentacion()`）
    - 呈现计数挂在 `RexSwitchPresentTick()` 旁边；关帧计数挂在
      `closed_frame_submissions_[(frame_current_++) % ...]` 旁边

## 四、判读规则

    cierres/presentacion ≈ 1 且 retraso 仍 ~1.7  → 环不是原因，换方向
    cierres/presentacion > 1                     → 确认"一次呈现关掉多个帧槽"
    fps 上去 + retraso 升到 4~6                   → 环深修复成功

## 五、下一轮的分叉（按结果）

    A. 环深修好了 → 继续找剩下的大头（顶点/图元 0.16 ms/绘制 已经很便宜；
       接下来是 GPU 侧：83 绘制/帧、剪刀 39 屏幕）
    B. 环深不是原因 → 那 30 ms 就是 GPU 真的需要这么久（每帧约 30 ms GPU 工作），
       方向转为砍 GPU 工作量（参考项目第 3 步），或者把等待改成不等（异步提交、
       拉长环、三槽并行）
