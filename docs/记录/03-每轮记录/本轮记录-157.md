## 一、版本 62 的两个结果，一正一反转

### 正面：帧环的修复成功了

    [perf] ANILLO presentaciones=N cierres=M  cierres/presentacion=1.00   （23 行，0.98~1.00）
    [perf] FENCE  →  一行都没有

解读：

- `cierres/presentacion = 1.00` → 环**确实是"一次呈现推进一格"**，
  上一轮"环被多消费"的猜测**被推翻**（这个我们必须记住，别再猜它）。
- FENCE 一行都没有 → 说明 `BeginSubmission` 里那种阻塞等待**几乎消失了**
  （每 30 次才打一行；这次全程不到 30 次）。**CPU 那边的等待问题被修掉了。**

### 反转：帧率没有一点变化

    154 号（环深 3）：13.22 fps，80.8 绘制/帧 → 归一化 13.34
    155 号（环深 6）：13.93 fps，88.0 绘制/帧 → 归一化 13.33
    → 完全一样。

**把 CPU 的等待拿掉，帧率不动 → 说明那个等待是"症状"而不是"病因"。**

## 二、那么现在是谁在定帧长

155 号主菜单时段的观察：

| 指标 | 数值 | 含义 |
|---|---|---|
| CPU total | 90~127%（400% 满） | **只用了约 1 个核**，CPU 没跑满 |
| libnx `fences esperadas` | 385~560 ms/s | CPU 在等**呈现**的 fence（`nvFenceWait`），不是提交的 fence |
| 每帧 | 73~87 次绘制、29~44 个屏幕的剪刀、1 次 resolve | GPU 侧的活 |

`cod6_saltar_dibujos`（一次都不画）= 61.7 fps = 16.2 ms/帧，而现在 71.5 ms/帧。
→ **绘制相关的部分（GPU 工作 + 呈现）占了约 55 ms/帧，CPU 只占约 1 个核。**

**结论：主菜单现在受 GPU（或呈现节奏）限制，不是 CPU。**
88 次绘制 / 71.5 ms ≈ **每次绘制 0.8 ms 的 GPU 时间**——对几十个小四边形来说，
这个数量级不像是"画像素"，更像是**每次绘制的固定 GPU 开销**（状态切换/屏障/EDRAM 模拟）。

## 三、顺手看到关卡内（用户这次又进关了）

    por fotograma: 5762 dibujados | tijera 3279 pantallas | 11.0 resolves (6 pantallas) |
                   43.2 render targets | 284 transfer dibujados | 21.85 MB subidos
    帧长 2.5 秒（0.4 fps），CPU total 68~71%

关卡内每帧 5762 次绘制、**3279 个屏幕的剪刀面积**、11 次 resolve、43 个渲染目标。
这就是 0.5 fps 的全部来源——和 CPU 无关，是"模拟层每绘制 + 每渲染目标"的成本乘以数量。

## 四、下一步：唯一还缺的数字是"GPU 真实每帧时间"

现在所有推理都卡在一个未知数上：GPU 每帧到底占多少 ms？

- 若是 ~70 ms → 只能砍 GPU 工作（自研渲染器 / 简化着色器 / 减少 pass）。
- 若是 ~20~30 ms → 那么帧长是被"呈现节奏"顶住的，有便宜的改法（提交/呈现策略）。

**版本 63 就是量这个**：用 Vulkan 时间戳查询（timestamp query）在每帧首尾打点，
读出 GPU 真实耗时，并按 pass 汇总。这是最后一个"猜不出来、只能测"的数。

## 五、给用户的实话

1. 帧环这条线到此为止：修好了，但没有性能收益，**但排除了一个方向**，也把 CPU 侧的疑点清空了。
2. 主菜单现在的墙在 GPU/呈现，不在 CPU。
3. 关卡内的墙是 `5762 次绘制 × 每次 0.4 ms` 这个乘数，**除了自研渲染器没有别的解**。
4. `什么时候能玩.md` 里的三个里程碑不变；这一轮把"① 帧环修复"从"待验证"变成"已验证但无收益"，
   所以真正能让主菜单变快的只剩"② 渲染器接管 UI 小绘制"。
