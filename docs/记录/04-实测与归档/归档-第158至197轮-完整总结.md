# 二、这一段真正达成的成果

## 1. 打通了"自研渲染器画游戏内容"的完整链路（v93 验证）

    读客机顶点（大端） → 解格式 → 像素坐标 → 取纹理 → 按游戏 render pass 建管线
    → 自己的 SPIR-V 着色器采样 → 画出位置/图案正确的 UI

证据：v93（`md5 b3be5066329479107688dd767325f05d`）时日志
`CUENTA92: con_tex=800 sin_tex=0 sin_pipe=0 sin_set=0 rect0=0 pintados=800`，
用户确认"画面看起来和原版一样"（即我们画的 UI 正确），模拟层那 10 次绘制被撤掉。

## 4. 顶点/纹理格式（已完全解出）

    顶点 stride = 32 字节（8 dwords）
      偏移 0  ：位置 4×float32（x, y 是**屏幕像素坐标**，z=0，w=1）
      偏移 16 ：颜色 4×uint8（RGBA）
      偏移 20 ：UV 2×float32
    索引：16 位**大端**（不换字节序会读成 768/512/256 而不是 0/1/2/3）
    像素→NDC 的变换在 VS 常量里：c0=(2/1280,0,0,-1)，c1=(0,-2/720,0,1)

# 三、失败清单（每条都烧过一轮，别再踩）

| 失败 | 现象 | 原因 | 教训 |
|---|---|---|---|
| toml 被写坏 | 黑屏、零帧 | `invalid utf-8` → 整份配置失效 → `gpu_plugin` 为空 → GPU 插件不加载 | 现在代码里已兜底；先查日志 `Failed to parse config` |
| 实验开关留在交付 toml | 黑屏 | `cod6_saltar_dibujos = true` 忘了删 | **出包前检查 toml 有效键** |
| netloader 推 nro | 启动黑屏、日志不更新 | 上传不完整（`nxlink` 停在 34.42% 就返回 0，无校验） | **nro 一律线缆** |
| MTP 写卡 | （实际没写坏，但过程卡死） | `CopyHere` 异步，进程被杀 | **MTP 只读** |
| 在 present 时采样纹理 | UI 图案乱码、夹杂别的元素 | 游戏为每个元素复用同一块纹理内存，present 时已被覆盖 | **纹理只在绘制那一刻有效** |
| 在模拟层绘制之前接管并 `return`（v96） | 文字全乱 + 洋红块 | 模拟层缓存了"已绑定的状态"，我们改了它不重新绑定 | **不能只跳过记账**，要么完全拥有状态机 |
| 在 `IssueSwap` 里画 | 无像素、帧率不变 | 那里没有活动的渲染目标 | 落点是 presenter 的 render pass 或游戏自己的 pass |

# 四、三堵墙（决定项目走向）

1. **模拟层每绘制成本**：0.42 ms（关卡）/ 0.6~0.8 ms（菜单），其中约 80% 是准备工作。
2. **GPU 侧**：菜单全跳过绘制时 38~44 fps → 说明 GPU/提交不是瓶颈。
3. **游戏自身 CPU**：关卡内一次不画也只有 **14~15 fps**（1.7 核摊在约十个线程上）。

**因此**：
- 菜单能不能到 40 fps：**能**，但前提是**完全拥有渲染路径**（见下）。
- 关卡能不能到 30 fps：**不能**，除非把游戏热函数也原生重写（参考项目第 7 步），而且是月级投入。

# 五、剩下的两条路（需要项目所有者决策）

| 路线 | 内容 | 工作量 | 结果 |

| **A. 寄生（现状）** | 只在模拟层旁边追加绘制 | 已做完 | **永远 14 fps**（80% 成本绕不开） |

我们这一段证明：**A 已经到顶，B 是唯一有意义的下一步**。
