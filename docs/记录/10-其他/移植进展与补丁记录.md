### 最后一块拼图：`netshim.c` 的两条规则

之前所有版本都错在同一个地方 —— **改了不该改的 socket**。

| 规则 | 错误做法（导致黑屏） | 正确做法 |
|---|---|---|
| **`recvfrom` 没数据时返回什么** | 返回 `-1` + `EAGAIN` → 游戏判定为致命错误 → `Com_Error: "Failed to recvfrom() socket, error %s.."` → longjmp → 重启/退出 | **返回 `0`**（空数据报）。游戏只检查负数，0 表示"暂时没数据" |
| **改哪些 socket** | 改**所有** socket → SDL 的 X11 连接（unix socket）被假装成功 → `SDL_InitSubSystem(SDL_INIT_VIDEO) failed: x11 not available`，窗口都开不出来 | **只改 `AF_INET`/`AF_INET6`**，unix socket 一律放行（`getsockname` 判断） |

这两条一改，画面立刻出来。

## 一、重大突破：违例从 1261 万 → 0

### 问题本质

游戏在初始化后**拆掉了自己的渲染子系统**（虚析构 `sub_82095300` → `sub_82095330`），
但**工作线程还在继续使用它**，于是：

```
sub_82095228 + 513   → 写入全局 0x83E4E9AC = 0x6C808DA4   （有效指针，初始化成功）
sub_82095330 + 4871  → 写入全局 0x83E4E9AC = 0x0          （拆掉，清零）
工作线程 sub_820AF938 → lwz r10,-5716(r27) = 0
                     → lwz r11,60(r10)  = 读客户机地址 0x3C   ← 每秒 7 万次
```

### 定位手段（可复用）

| 手段 | 用法 |
|---|---|
| **硬件写断点** | `watch *(unsigned int*)0x183E4E9AC`（客户机 0x83E4E9AC + base 0x100000000）→ 抓到写入者 |
| **条件信号捕获** | `catch signal SIGSEGV` + 判断 `$_siginfo._sifields._sigfault.si_addr`，只在目标地址上停 |
| **从镜像读字符串** | 错误路径里 `r4` 指向的格式串，直接从 `/opt/dump/cod6_image.bin` 读出来 |
| **PPCContext 布局** | **`r3` 在最前**（`r3,r0,r1,r2,r4...`），不是 r0 打头 —— 之前解读错就是栽在这 |
| **perf 无扰动采样** | `/usr/lib/linux-tools/6.8.0-147-generic/perf`（WSL2 专用包不在源里，用这个二进制） |

## 二点五、★★★★★ 决定性修复：setjmp / longjmp 路由

### 问题

MW2 在 `Com_Error` 恢复时用 `longjmp` 跳回 `setjmp`。静态重编译**无法跳进 C++ 函数中间**，
所以这两个函数必须交给运行时的 `ppc_setjmp` / `ppc_longjmp` 处理。
**没声明时，guest 的 longjmp 会从过期的 LR 返回，把栈指针一路往上抬**：

```
正常: sub_82283648 入口 r1 = 0x7015FD40 → stwu -208 → 0x7015FC70 ✓
故障: 同一条链，r1 整体高 0x350 → r1 = 0x7015FFC0，栈顶 0x70160000
      → 可变参数函数存 r5..r10 到 r1+0x40 = 越过栈顶 = 护栏页
```

这条正是 bo2zm-nx 移植在 overrides 里写下的经验：
> 没有它们，第一次启动 3 秒就写坏内存。

### 怎么找到这两个函数（可复用手法）

1. **setjmp**：在镜像里扫「以 r3 为基址、连续 `stfd fX` + `std rX`」的函数
   → `0x823DFF10`（存 f14-f31 到 0..136(r3)，r13-r31 到 152..296(r3)，再用 `stvx128` 存 v64-v127）
2. **longjmp**：扫它的镜像（连续 `lfd` + `ld`）→ `0x823E08C0`
3. **关键一步：用 `bl` 目标核对**。我一开始把 setjmp 写成 `0x823DFF08`（上一个函数的尾巴），
   结果 codegen 生成了 23 处 `ppc_longjmp` 却**零处 `ppc_setjmp`** → 运行到 longjmp 时
   找不到已注册的 jmp_buf → **直接 abort（退出码 134）**。
   扫 `bl` 目标后确认真实入口是 **`0x823DFF10`（被调用 14 次）**、longjmp 是 `0x823E08C0`（22 次）。

### 结果

```
overrides.toml:
  setjmp_address  = 0x823DFF10
  longjmp_address = 0x823E08C0

生成: ppc_setjmp 14 处、ppc_longjmp 23 处
运行: 违例 0 ✓   不再 abort ✓   三条图形管线建立 ✓   音频正常 ✓
```

**栈破坏与空转风暴彻底消失**，游戏现在是干净地 unwind 后退出（`Execution complete`）。

游戏能正常启动、建管线、走完初始化，然后**干净退出**（约 0.2 秒）。

**从「一个像素都不出」变成「三条图形管线建起来了」。**

## 二点七、宿主层网络补丁 `netshim.c`（不再改游戏代码）

逐条给网络函数打桩是错的方向 —— 它制造了两个新 bug：
`XNetGetTitleXnAddr` 返回 0 让 `loc_8230FA34` 变成 do/while 死循环（占 12.8% CPU），
`WSAStartup` 打桩没填 WSADATA 让版本号读成 21.112。

正确的做法是在**宿主边界**修：`LD_PRELOAD` 拦截 socket 调用。

```
bind      → 总是返回成功（"WARNING: Couldn't allocate IP port" 消失）
setsockopt→ 总是返回成功（"Failed to set socket to broadcast-capable" 消失）
recvfrom  → 强制 MSG_DONTWAIT，没数据就返回 EAGAIN
            （这是黑屏的直接原因：Main XThread 阻塞在 recvfrom，
             不返回就永远不进入帧循环，实测只提交 1 帧）
ioctl/connect/listen/sendto/accept → 同样兜底
```

效果：

```
违例 0，Com_Error 无，longjmp 无
New controller connected to slot 0.
[VDSWAP] 60 秒内 121 次   ← 帧循环真的跑起来了
```

## 二点八、黑屏的真正原因（已定位到具体证据）

| 观测 | 数据 | 含义 |
|---|---|---|
| `VdSwap` 调用 | 60 秒 121 次 | **帧循环在跑**（约 2 FPS） |
| 图形管线 | 只有 3 条 | 菜单会需要几十条 → **游戏几乎没提交绘制** |
| 打开的数据文件 | `common.ff` `ui.ff` `code_post_gfx.ff` `patch.ff` + 4 个 `.pak` | 确实在读游戏数据 |
| perf 采样 | 无单一热点 | 主线程是**阻塞等待**，不是在算 |
| 主线程栈（修网络前） | `recvfrom()` | 卡在等 LAN 数据 |
| 主线程栈（修网络后） | 游戏跑到渲染器初始化后停住 | 卡在 GPU 侧等待 |

**结论**：游戏卡在渲染器初始化（`----- Initializing Renderer ----` 之后），
D3D 写出的环里没有真正的绘制，所以模拟 GPU 只能呈现黑帧。
这与 nfsmw-nx 文档写的一致：**游戏会等 GPU 写一个值（WAIT_REG_MEM → SCRATCH_REG），等不到就冻结**。

## 二点九、音频 / 录制结论

- 运行时确实在推音频：日志有 `audio endpoint 'ALSA default playback device': 6 ch, 48000 Hz`
- 但 **WSL2 里没有声卡**（无 `/dev/snd`），ALSA 只能挂 null 设备 → **听不到、也录不到**
- 尝试过三条路都不通：ALSA `file` 插件不落盘、`SDL_AUDIO_DRIVER=dummy` 不被支持、`SDL_AUDIO_DRIVER=disk` 不生成 `sdlaudio.raw`
- **录屏可以**：每轮 6 帧 PNG + contact.png 都在 `NSMW2\frames\`
- 换个有真声卡的环境（Windows 本机）就能听到 BGM

## 三点五、黑屏排查：已排除项与已证明项（都用硬数据）

### 已证明（这些不是猜测）

| 事实 | 数据来源 |
|---|---|
| 帧循环在跑 | `VdSwap` 探针：60 秒 **121 次** |
| **游戏只提交过约 3 次绘制** | 插件日志「Creating graphics pipeline state」**只有 3 条**（每条 = 一组新着色器首次使用） |
| 游戏在读游戏数据 | `/proc/PID/fd` 里有 `common.ff` `ui.ff` `code_post_gfx.ff` `patch.ff` + 4 个 `.pak` |
| 输入/音频已初始化 | `New controller connected to slot 0`、`audio endpoint ALSA 6ch 48000Hz` |
| 渲染器初始化**返回了** | 二分探针：`sub_82132158` 里 printf / `sub_8238EED0` / `sub_822E1F80` **三个调用都正常返回** |
| 游戏在 6~9 秒后自己退出 | `Execution complete` |

### 已排除（附证据）

| 怀疑 | 结论 |
|---|---|
| 中文路径 | 复制到纯英文 ext4 路径，行为完全一致 |
| swapchain 格式不对 | format 44 = `VK_FORMAT_B8G8R8A8_UNORM`，正常 |
| Xvfb 缺 Present 扩展 | **有** Present、MIT-SHM（缺 DRI3/GLX），且 swapchain 创建成功 |
| presenter 的 cvar | `present_render_pass_clear=false` / `present_effect=none` / `present_dither=false` 全试，仍黑 |
| `KeWaitForSingleObject` 是黑屏原因 | **不是** —— 它只出现 6 次且发生在**退出路径**上 |
| `VdSwap` 的 r3 是命令缓冲 | **不是** —— dump 出来是 224 字节的头结构，99.2% 为零 |

### 两个失败的工具尝试（教训）

1. **`vkshim.so`（LD_PRELOAD 拦 Vulkan）无效** —— 插件是 `dlopen` 后用 `vkGetDeviceProcAddr` 取函数指针，
   把 `vkGetDeviceProcAddr`/`vkGetInstanceProcAddr` 也拦了仍然没用（dlsym 从 handle 取符号）。
   要真拦必须写 **Vulkan layer**（implicit layer + `VK_LAYER_PATH`）。
2. **在 `sub_82132158` 入口读 `r4` 永远读到垃圾** —— 那个字符串是**函数内部**才 `lis/addi` 进 r4 的。

### 结论

**黑屏 = 游戏从来没画过菜单**（只画了 3 次初始化的东西），不是呈现层的问题。
游戏在 6~9 秒后自己 `Execution complete` 退出。下一个要回答的问题是：
**它在退出前那几秒在等什么 / 决定退出的条件是什么。**
| WSL1 无法映射客户机内存 | 死循环 | 已升级 WSL2 |

## 四、当前卡点（正在修）

### 4.1 已解决
- `[FATAL] Call to invalid or unregistered function at guest address 0x820AFE98`
  → 已加入 `overrides.toml` 重新 codegen

### 4.2 进行中（故障地址在漂移，说明在逐步深入）

| 轮次 | 故障 | 含义 |
|---|---|---|
| r18 之前 | `read of 0x3C` | 全局 0x83E4E9AC 被清零后工作线程读它 |
| r19 | `write of 0x823F1800` | 落在镜像**代码段**（只读页）—— 指针算错 |
| r20 | `write of 0x70160000` | 落在**栈底之外** —— 栈溢出，多半是深递归 |

**故障地址一路往前走，说明补丁确实把游戏往里推了，每一层都是新的问题。**

#### P5：可变参数函数的栈顶越界（已修）

实测寄存器：

```
r1 = 0x7015FFC0        栈指针，离栈顶 0x70160000 只差 64 字节
故障地址 = 0x70160000 = r1 + 0x40
```

`sub_82280900` 是**可变参数函数**，按 PPC ABI 要把 `r5..r10` 存到
`r1+32 … r1+72`（调用者参数保存区）。但它是线程栈最外层的调用之一，
`r1+64` 正好越过栈顶 → 每秒约 3 万次写故障。

修法：进入函数时 `ctx.r1.s32 -= 0x80`，退出时 `+ 4208 + 0x80` 补回来。
修完这个故障消失，游戏推进到下一层。

#### 当前故障

```
sub_82281160 + 44  (cod6_recomp.52.cpp:20470)  read of 0x0
调用链: sub_82284538 → sub_82283648 → sub_82281160
r3 = 0x7015fcc0_00000000   ← 32 位栈地址跑到了 64 位寄存器的高半部
r1 = 0x7015fc70
```

`r3` 的形状（高 32 位是栈地址、低 32 位为 0）说明**某处把 32 位值当成 64 位用了**。

#### 两次失败尝试（都留下结论）

**P5b（把 r1 下移 0x80）**——失败，但有价值：
`sub_82280900` 的 `va_list` 是按 `addi r10,r1,4240` 定位参数保存区的，
r1 一移位，**参数就读错**，`sub_82281160` 收到的指针变成 `0x7015fcc0_00000000`
（正是 `0x7015FCC0` 被放进了 64 位寄存器的高半部）。**已回滚。**

**P6（mmap 栈顶那一页）**——失败，但结论重要：
`mmap(MAP_FIXED)` 在 `0x170160000` 上**成功**了，故障却依旧。
说明运行时判定访客内存越界**走的是自己的地址表，不是 MMU**，
所以从外面补映射没有用。

#### 现在的干净基线

P1–P4 保留（PM4 空指针风暴已消除），P5/P6/探针全部回滚。
当前是 `write of 0x0`，约 84 万次/25 秒。

**下一步方向**：这条 printf 链上 r1 只比栈顶低 64 字节，
说明调用者 `sub_82283648` 的栈帧分配与原始 PPC 不一致（它自己 `stwu r1,-208(r1)`，
按理 r1 不该贴着栈顶）。**核对 `sub_82283648` 的 PPC 与生成代码的帧分配**。

### 已排除：中文目录

把 6.9 GB 游戏数据完整复制到 WSL 内 ext4 的纯英文路径 `/opt/game/cod6_en` 后，
行为**与走 `/mnt/d/主机掌机/...` 中文路径完全一致**（同样 `write of 0x70160000`，同样 186 万次违例）。

**结论：中文路径不是原因。**
