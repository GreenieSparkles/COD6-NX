## 这一版想验证的核心假说

**进任务崩 + 帧数极低，可能都是**同一个**原因：游戏在反复访问客户机地址 `0x0~0x1000`
（零页），而 SDK 默认把零页设成「不可访问」，于是每次访问都是一个 CPU 异常（约 9 µs）。**

**证据：72 号的故障地址按低位拆开全是 `基址+0x000 / +0x01C / +0x02C / +0x1000`。**

**对应两个配置（已生效）：**

```toml
protect_zero = false        # 零页可读写
switch_vigilancia = false   # 关闭页监视（另一条异常来源）
```

## 已完成（按时间）

### 平台层
- `socketInitializeDefault()` / `nifmInitialize()` 补上（原先没调用 → `socket()=-1 errno=2`）
- 特权端口 `<1024` 的 `bind` EACCES → 透明重定向到临时端口
- `recvfrom` 长度超出映射范围 EFAULT → 中转缓冲
- 无数据时 `recvfrom` 返回 0
- `XamLoaderLaunchTitle("default.xex")` 忽略（P8）
- **`NETSELFTEST` / `BIND_ERRNO` / `RECVFROM_*` 全部为裸 `write()` 日志**

### 构建网
- `-mtp=soft`
- codegen 在 WSL 内可跑：`D:\rexglue-linux\linux-amd64\bin\rexglue`（7.5 秒，18,848 函数）

- **`dentro_GPU` = 98~99%**（时间全在模拟 GPU 里）

### 崩溃定位（72 号）—— **注意：之前的符号化是错的，已纠正**

```
五个崩溃记录（同一份 rex_crash.log 累积了五次运行），全部同一条指令：
    instruccion 0xb9402f01  = ldr w1,[x24,#0x2c]
    far dentro de la memoria del invitado: 0x0000002c
    x3/x19/x21 = 0
```

**关键教训：`imagen+偏移` 必须对同一版 ELF 符号化。**
**72 号的崩溃来自旧构建，用新 ELF 对出来的 `sub_82384500` 是错的** ——
反汇编新 ELF 的 `0xb0f890` 是 `mov w3, #0x1080000`，根本不是那条 `ldr`。

**已经做的补救：**
- 每次 `d.sh` 部署会把带符号的 ELF 存到 `符号存档\cod6_<nro md5>.elf`
- 崩溃报告开头加 `build <日期> <时间>` 标记
- 符号化工具：`python3 /mnt/d/devkitPro/tools/symbolice.py <elf> 0x<b0f890> ...`（可用，实测 65,873 个符号）

### 关键发现：COD6 不走 D3D

```
生成代码里 __imp__D3D* 引用数: 0
SDK 导入表里 D3D 条目:        73（COD6 一个都没用）
```

**结论：COD6 直接手写 PM4 环，不经过 D3D 运行时。**

**这决定了原生渲染器的做法：**
- nfsmw/COD4 那套要 hook 游戏的 D3D 函数（因为它们的游戏确实调用 D3D）
- **COD6 不需要 D3D hook** —— 只要读它写的 PM4 流，所以 CENSO 统计出来的 opcode 分布，
  就是原生渲染器要覆盖的命令清单

## 第 5 轮：找到了崩溃和 "98% GPU 时间" 的**同一个根因**

### 证据链

**72 号的日志里有这一组：**

```
[gm] svcSetProcessMemoryPermission fallo #1 (0x0000D401) en 0x2ee69d4000
[gm] svcSetProcessMemoryPermission fallo #2 (0x0000D401) en 0x2ee69d5000
...                                          #8
```

**而 SDK 自己的注释（`guest_memory_switch.cpp`，作者写的）写着：**

> With the page read-only, watching works the same (the write faults and the handler services it)
> but reads are free.
> **Why it is not a given. `svcSetProcessMemoryPermission` only accepts memory whose state allows
> permission changes.** The views are mapped with `svcMapProcessMemory`, and whether Horizon allows
> it there too is not documented anywhere.
>
> Measured in a race: **108,000 emulated reads per second at about 9 µs each, which is practically
> the whole core of the main thread.**

**再看同一文件的另一段注释：**

> Measured on hardware: the mode ends up as "desmapeo" (every read of a watched page faults), and
> **with five threads that overruns libnx's eight exception slots — its entry then spins for ever at
> 100% CPU and the faulting thread never resumes**
> (seen in the stack samples: `__libnx_exception_entry+0x9C`).

### 和观测完全对上

| 观测 | 注释描述 |
|---|---|
| `0xD401` × 8 次失败 | 内核拒绝改权限 |
| **五个线程**同时死在同一条指令（3013/3317/622/711/861） | "with **five threads** ... overruns libnx's eight exception slots" |
| 死在同一地址 `[基址+0x2C]` | 被 desmapeo 的页，读到就异常 |
| `dentro_GPU` 98~99% | "practically the whole core of the main thread" |

**结论：COD6 不是「画得慢」，是被页异常拖死的；崩溃也是同一个原因。**

### 修法：`switch_vigilancia`

`guest_memory_switch.cpp` 里加了 cvar（默认 true = 原行为），并在 `RexGmProtect` 开头短路：

```cpp
if (!REXCVAR_GET(switch_vigilancia)) return true;   // 不登记任何被监视页
```

**这样页面永远保持 mapeadas + 可读写：没有 desmapeo、没有读异常、没有五线程撞死。**

**代价：CPU 写内存不再被自动发现，coherence 靠显式交换（MakeCoherent / resolve）。可能个别纹理不刷新，但换来游戏不崩、不吃满核心。**

```

cod6.toml  4,901 字节  14 项（新增 switch_vigilancia = false）
```

## 第 6 轮：**页异常假说被日志直接证实**

### 72 号日志里的关键三行

```
[gm] permisos no disponibles (ultimo 0x0000D401); modo desmapeo      ← 进入了 desmapeo 模式
[gm] DIAG_FALLO protegida: win=0xBFB9C280 paginas_protegidas=1417
[gm] DIAG_FALLO protegida: win=0xBFBB4A74 paginas_protegidas=2465
```

**`paginas_protegidas` 随时间从 1417 涨到 3073，最大 3233。**

**3233 页 × 4 KB ≈ 13 MB 的客户机内存在 desmapeo 模式下是**不可读的** —— 游戏每读一次就触发一次异常，SDK 作者实测每次约 9 µs。**

### 完整因果链（每一环都有日志或注释证据）

```
svcSetProcessMemoryPermission 返回 0xD401（内核拒绝改页权限）
   ↓ （8 次失败后）
SDK 进入 "desmapeo" 模式
   ↓
被监视的页从视图里 unmap（最多 3233 页 ≈ 13 MB）
   ↓
游戏读这些页 → CPU 异常（~9 µs/次）
   ↓
① 主线程核心被吃满 → dentro_GPU 看起来像 98~99%
② 多线程同时异常 → 超出 libnx 8 个异常槽 → 五个线程卡死在同一指令 → 进程死亡
```

**这就是「帧数极低 + 进任务就崩」的同一个根因。**

### 第 5 轮已经做的修

**`switch_vigilancia = false`**：`RexGmProtect` 直接返回，不登记任何被监视页 →
**不 unmap、不异常、不撞槽。**

### 第 6 轮补的度量

- `switch_vigilancia=false` 后这个数应该接近 0（只剩首次映射页的少量异常）

## 第 11 轮：重新看 72 号的故障地址 —— **线索指向「零页」**

### 重新解读这三行

```
[eh] #1 fault: pc=0x5ACF67E63C far=0x2EF69D401C esr=0x92000045
[eh] #2 fault: pc=0x5AD0B80508 far=0x2EA69D4000 esr=0x92000045
[eh] #3 fault: pc=0x5AD0B80508 far=0x2EA69D5000 esr=0x92000047
```

**把 `far` 的低位单独看：**

```
...D401C   →  基址 + 0x01C
...D4000   →  基址 + 0x000
...D5000   →  基址 + 0x1000
```

**都是**客户机第 0 页附近**（偏移 0x0、0x1C、0x1000）。**

**崩溃点 `far = 0x2E769D402C` 就是基址 + **0x2C**。**

### 这说明什么

**游戏在反复访问客户机地址 0x0 ~ 0x1000 —— 也就是「零页」。**

**而在真正的 Xbox 360 上，低地址是**有效内存**（内核加载器数据），游戏合法地在用。**

**我们的默认配置 `protect_zero = true` 把零页设成「不可访问」：**

```cpp
// xmemory.cpp:230
heaps_.v00000000.AllocFixed(0x00000000, 0x10000, 0x10000,
    kMemoryAllocationReserve | kMemoryAllocationCommit,
    !REXCVAR_GET(protect_zero) ? (Read | Write) : NoAccess);   // ← 默认 true = NoAccess
```

**结果：游戏每碰一次低地址就是一个 CPU 异常（约 9 µs）。**

### 所以第 5 轮那个修复可能才是主因

**`protect_zero = false`（第 5 轮已部署）让零页可读写 → 这些异常直接消失。**
**`switch_vigilancia = false`（同轮）是第二道保险。**

### 优先判读顺序（下次运行）

1. **`[eh] TOTAL fallos=`** —— 如果接近 0，说明就是零页
2. **`[perf] DIBUJOS` 平均耗时** —— 是否从 0.73 ms 掉下来
3. `[eh] AVISO` 有没有出现

### 静下来想一想的意义

**如果这条成立：我们从一开始就在被「零页保护」这一个默认值拖死 —— 那不是渲染器问题，
不是模拟器架构问题，是一个 cvar 的默认值不适合这个游戏。**

**MW1 能跑，很可能就是因为它的 SDK 版本默认 `protect_zero=false`，或者它根本不碰低地址。**

# ★ 突破：进任务崩溃的真正原因，已实证 —— `protect_zero = false`

## 证据链（76 号崩溃报告，build 12:36:50）

```
funcion de invitado: __imp__sub_821254B0
instruccion 0xb9402f03          (ldr w3,[x24,#0x2c])
far dentro de la memoria del invitado: 0x0000002c
x3 = 0
```

**把 `sub_821254B0` 反编译出来：**

```asm
lwz   r11,44(r4)      ← 崩的就是这条
cmpwi cr6,r11,0
beqlr cr6             ← 计数为 0 就安全返回
...
stw   r6,44(r4)
```

**这是一个容器的 `pop_back` 类方法：读对象偏移 44 的计数，为 0 就返回。
游戏调用它时 `r4 = NULL`。**

## 为什么真机能跑

| 平台 | 读 `[NULL + 44]` |
|---|---|
| **真机 Xbox 360** | 地址 44 是**已映射的内核低端内存**，值为 0 → `beqlr` → **安全返回** |
| **我们（`protect_zero = true`，SDK 默认）** | 零页不可访问 → **读异常 → 进程死亡** |

**整场战役里「五个线程同时死在 guest 0x2C」就是这个：
游戏在合法地调用空对象方法，真机靠低端内存兜底，我们把低端内存封了。**

## 修复

```toml
protect_zero = false
```

**用户实测：`这次进入主菜单了啊`。**

**从「进任务必崩 / 主菜单极卡」到「能进主菜单」，这是本会话第一个实证性的功能修复。**

|---|---|

## 下一步：原生渲染器，阶段 1

按 `native-renderer.md` 的次序：

1. 自己的 GraphicsSystem 注册 MMIO `0x7FC80000`
2. 消费 PM4 环（COD6 不走 D3D，直接写环 —— 我们只需要环，不需要 D3D hook）
3. 应答 GPU 写回：`MEM_WRITE` / `COND_WRITE` / `REG_TO_MEM` / `EVENT_WRITE_*`

- 环线程优先级 **0x2D**（呈现 0x2C，客户机 0x3B）
