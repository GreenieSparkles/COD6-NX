## 一、这个项目是什么

把 Xbox 360 版 COD6（MW2，Title ID `41560817`）移植到 Switch。

```
default.xex → ReXGlue 反编译成 C++（131 个文件）→ 交叉编译 ARM64 → cod6.nro
         → Switch 上 ARM64 原生执行 + Vulkan → Mesa/NVK → Tegra X1
```

**链路与 COD5/COD4 移植者一致：**ARM64 原生程序 → 自写渲染器 → Vulkan → Mesa/NVK → GPU。
**我们只差"自写渲染器"这一环。**

## 五、实测表现（这是真相，别相信任何"已经可用"的说法）

| 场景 | 帧率 | 说明 |
|---|---|---|
| **主菜单** | **11–14 fps** | 画面正常、可操作 |
| **关卡内** | **0.5 fps** | 能进、能看到准心/HUD、不能玩 |

**关键结论：关卡内 73 ms/帧里，绘制最初占 2080 ms，游戏自身逻辑占 73 ms。

主菜单 13 fps 的 75.9 ms/帧里，绘制（`en_draw`）占 ~60%，其中 64% 是
「发出 vkCmdDraw 之后」的尾部，而且集中在**每两帧一次、一次约 60 ms 的单次绘制**上。

## 六、重大发现（按重要性）

1. **主因定案（150 号 / 版本 57 实测）：memexport 的 CPU 读回是最大的一笔。**
   401 次「超 2 ms 的绘制」共 21,120 ms（整机墙上 46.8 s 的 45%），其中
   **175 次带 memexport = 16,405 ms，99% 落在 `cola` 段**，那段就是
   `IssueDraw_MemexportReadbackFastPath/FullPath` —— fast 路径在上一槽提交未完成时退回
   full 路径 → `AwaitAllQueueOperationsCompletion()` 等 GPU。平均 94 ms、中位 109 ms。
   默认 `readback_memexport = true`，toml 里从来没关过 → **版本 58 关了**。
2. **次因**：另外 226 次（4,714 ms）**全部耗在「发出绘制之前」**，平均 21 ms。
   版本 58 加了 `vfetch` / `barreras` 拆分，等下一次日志定。
3. **被推翻的假设**：`inval_todo=0` 出现在全部 401 条、`media_inval=0.00`
   → `RangeWrittenByGpu(0, 512 MB)` 那条整块失效分支一次都没执行。别再往那个方向查。
4. **绘制时间是双峰**（149 号日志，217 窗口）：每 120 次绘制里 <0.1 ms 的 112~115 次，
   ≥20 ms 的 0.9 次。所以"平均每次绘制 1.25 ms"是统计错觉。
5. **`RESTO_SPLIT` 证明**「管线配好 → 发出 vkCmdDraw」平均 **0.010 ms**（累计 18,840 次）。
6. **上一轮的插桩有 bug**：`fase5` 写在 `return` 之后是死代码（57 已修）；
   FASES 行括号里的 `vert/tex/resto_prep` 恒 0.0，别引用。
7. **`log_level` 曾经是假开关**（Switch 分支忽略参数）→ 修成编译期删除，**8.60 → 12.43 fps**
8. **`svcSetProcessMemoryPermission` 返回 `0xD401`** → 页监视只能用"取消映射"，
   每次读 4 字节 = 一次异常（实测 167,405 次/秒）；上传纹理要 8 秒。
9. **`protect_zero = false`** 必需（游戏会读 `[NULL+44]`）
10. **小绘制形态**：`tipo=0`（无索引缓冲）、**1 个顶点**、`prim=1` → 顶点着色器展开成方块
11. **cvar 必须 `kHotReload`**，`kInitOnly` 拿不到 toml 的值（白查过一次）
12. **`Cinematic` 线程白烧 CPU**：主菜单 46.3%、关卡内 76.8%（栈采样，136/137 号）
13. **参考项目用 FFmpeg 替换反编译的视频解码器**（`nfsmw_video_wmv3.cpp`，约 1,343 行）

**关键技术事实：**
- SDK 用 **动态渲染**（`current_render_pass_ == VK_NULL_HANDLE`）→ 管线要用
  `VkPipelineRenderingCreateInfo` 声明颜色/深度格式
- 管线建在 `Cod6CrearPipelineDepuracion(VkFormat)` 里，**必须在 `IssueDraw` 开头调用**
  （放在别处不执行）

## 八、待做（按优先级）—— 详细版见 `该做什么-对照参考资料.md`

**两条线，别混：**
- **主菜单**：天花板 61.74 fps（118 号，0 绘制）→ 差距全是模拟层每绘制成本 → **渲染器问题**
- **关卡内**：天花板 13.70 fps（128 号，0 绘制，73 ms/帧）→ 是**游戏自身代码**的开销 →
  就算渲染器做到 2 µs/绘制（5,142 次 ≈ 10 ms）也只有 ~12 fps，**必须同时做游戏侧 CPU**

1. **构建层（最便宜的一块肉，我们完全没做）**：
   - **direct calls**：`sub_X(ctx,…)` → `__imp__sub_X(ctx,…)`（只改没被 hook 的函数）。
     生成代码里 **55,205 次调用，0 次改写**；他们改写了 79,612/83,077。**这是 LTO 生效的前提。**
   - **LTO**：`-flto -fno-fat-lto-objects` + 链接 `-flto=2 -flto-partition=balanced`。现在 0 处 `-flto`。
   - 之后 PGO（两遍构建）+ 函数排序（`.ld` 第一行必须 `KEEP(*(.crt0))`）。
     他们这三样一起：30.3 → ~34 fps。编译器是 devkitA64 GCC 15.2.0，能支持。
2. **原生渲染器接管真实绘制**（他们的 1.5–1.8 µs/绘制 vs 我们 420 µs/绘制）：
   N3-1 顶点/索引读取 → 纹理 untiling+指纹 → 管线缓存+启动预热 → RT 替代 EDRAM/resolve 不拷贝 →
   三槽并行。**这是唯一能进关卡的路。**
3. **游戏侧 CPU**：最热游戏函数原生替换（带 guard）、busy wait 换真等待（我们的 `Cinematic` 线程 46–77%）、
   页故障路径（167k 次/秒读异常）。
4. **GPU 侧**：ZCULL（要重编 Mesa）、着色器常量走动态 uniform buffer。着色器预编译**暂不急**（`PREP3 shader=0.0 ms`）。
5. **PC 版**：他们第 1 步就是"先在 PC 上跑通"，我们的 `out/linux` 坏了、从来没跑起来过。
6. 别做：降分辨率、FP16/VRS、扩展动态状态；也别再用超频数字做判断
   （**我们日志现在是 CPU 1326 / GPU 768，就是超频状态**）。
