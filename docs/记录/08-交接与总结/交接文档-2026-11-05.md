## 二、今天最大的发现：**贴图 bug 在 NVK，不在我们的代码**

玩家反馈并复现：**同一份数据，deko3d 渲染正常，NVK 渲染贴图崩坏。**

这条把九天里所有"我们的代码可能有问题"的方向都推翻了。支撑它的证据链：

| 已排除 | 证据 |
|---|---|
| 贴图数据坏 | 导出解码：沙鹰 DXT5 干净、法线 BC5 干净（平滑度 324 vs 误解码 5.4） |
| 格式映射错 | 实机逐格式校验 `[route]`：8/8 与 nfsmw-nx 参照**完全一致** |
| 地址算错 | `[dtab]` 读的是实时寄存器，是游戏要的地址 |
| 绑定顺序错 | 翻译器 `binding = texture_count + i`，渲染器 `dstBinding = 0` 连续写，两边一致 |
| 反平铺 pitch 单位错 | nfsmw 注释明确 "tiled: pitch in blocks"，我们一致 |
| mip 层数错 | 无 mip 存储时只建 1 层（`COD6_LEVELCOUNT`，有实测熵数据） |
| 显存块别名 | `DestroyImage` 先销毁镜像再归还块，结构上不可能 |
| 描述符集键碰撞 | `[setkey]` 日志：每个 ps 的 key 都不同，无碰撞 |

**结论：数据对、格式对、绑定对、地址对，只有换驱动才正确。**

## 三、当前最可能的原因（驱动层）

NVK 在 Switch 上的**压缩纹理路径**（BC1/BC3/BC5）很可能是坏的。依据：

1. deko3d 用 NVN 硬件路径，NVK 走自己的 TilKr 实现；
2. 我们的贴图**全部是 BC 压缩格式**（DXT1/DXT4_5/DXN）；
3. 症状是"采到别的贴图"而不是"噪点"，符合**块地址算错**而不是解码错；
4. nfsmw-nx 的 35 文件补丁里有大量 `nvk_image.c` / `nvk_nir_lower_descriptors.c` 改动。

### 已经准备好的绕过方案（就差接线）

`src/native/nativo/native_bc_decode.h`（**已写好、语法通过**）：

```cpp
DecodeBc1  (DXT1   → RGBA8)
DecodeBc3  (DXT4_5 → RGBA8)
DecodeBc5  (DXN    → RG8)
```

**下一轮要做的接线（三处，约 60~100 行）：**

1. `GetHostFormat`：BC1/BC3 → `R8G8B8A8_UNORM`，DXN → `R8G8_UNORM`，新增 `Conversion::kBcXxx`
2. `RunUntile`（`native_textures.cpp` ~792 行起）：每个 4×4 块调用对应解码器，展开成 64/32 字节
3. `host_row_bytes` / 尺寸：按 RGBA8/RG8 重算，**否则写越界**

加 cvar `cod6_native_bc_decompress`，默认关，出问题一行退回。

**判定标准**：开启后画面正常 → 确认 NVK 的 BC 路径坏了，且我们有了绕过方案。
代价：显存与带宽上升（RGBA8 是 BC1 的 8 倍），先用 `r_picmip 3` 压住。

## 四、被证明走不通的方向（**不要再试**）

### 4.1 纹理驱逐：结构性死结

| 方案 | 结果 | 记录位置 |
|---|---|---|
| 不驱逐 | 显存涨到上限，后期分不到空间，崩坏 | v325 |
| 立即驱逐 | 已录制的命令缓冲仍引用被销毁的 view → GPU 读释放内存 → **越玩越坏** | v307 实测，v308 回退 |
| 延迟销毁（`Retire` 队列） | 已实现，仍然不够（贴图被丢弃后 guest 内存已被复用，无法正确重建） | `native_textures.cpp:1558` |

**根本原因**：我们没有保留贴图的 host 副本。nfsmw-nx 保留了（`struct Textura { std::vector<uint8_t> datos; }`），所以它能安全驱逐。

**要做真正的修复**：给每张贴图保存准备好的 host 数据，驱逐后从副本重传，不回去读 guest 内存。**这是一次重写级改动。**

当前妥协：`cod6_native_texture_evict_frames = 600`（cvar 低于 600 会被强制抬到 600，见 `kEvictFrames`）。

### 4.2 每帧清空描述符集缓存

v331 试过：CPU 从 27~34 ms 涨到 **53~58 ms**，画面无改善。**已回退**（v332 改为不重置描述符池）。

### 4.3 降低内部分辨率

nfsmw 实测与我们实测一致：**帧数不由分辨率决定**，降低只会更慢。

## 五、帧数：瓶颈在 CPU，清单已就绪

实测（v325~v332 日志）：

```
renderer CPU   19 ~ 58 ms      ← 瓶颈
GPU            8.7 ~ 15.0 ms   （真实值 = 报告值 × 1.627）
```

**每帧 GPU 有大量时间在等 CPU。** nfsmw 在同一套 Vulkan/NVK 上把每绘制压到 **16 µs**，靠的是：

| # | 做法 | 他们省下 | 我们 |
|---|---|---|---|
| 1 | 描述符 set **按差异写**（1 次代替 4 次） | 未量化 | ❌ 未做 |
| 2 | 常量缓冲重绑减少 **38~45%**（在 NVK 里打补丁） | 未量化 | ❌ 未做 |
| 3 | ring 线程上**禁止分配、禁止日志** | 未量化 | ❌ 有 25 处 `fmt::format` |
| 4 | 纹理指纹衰减到 **1/32 帧** | 66 µs → 4.2 µs/绘制 | ✅ 已有 |
| 5 | 管线启动预创建 | 113/113 就绪 0.3 s | ✅ 已有 |
| 6 | 多工作槽（各自 fence/上传缓冲） | — | ✅ 4 槽 |
| 7 | query pool 只重置本槽 | 2144 次 → 1.2 ms | ✅ 已有 |

**未做的四项是最直接的收益来源。**


```
REXGLUE_PLATFORM_SWITCH = ON
REXGLUE_USE_VULKAN = ON
```

## 八、日志怎么读

| 日志行 | 含义 | 正常值 |
|---|---|---|
| `per frame: renderer CPU X ms, GPU Y ms` | CPU 是瓶颈 | CPU 应 < 20 ms |
| `GPU 时间要 × 1.627` | NVK 时间戳单位不是 1 ns | — |
| `pool de texturas: N bloques ... M MB` | 显存占用 | < 250 MB |
| `freed by the budget since start` | 预算释放 | > 0 |
| `[evict] ... NO expulsadas: su memoria ... otra imagen` | 缓存里有 guest 内存已被覆盖的条目 | 越多越糟 |
| `[texmon] subidas=N ... hash: X cambio, Y igual` | 上传次数/内容变化 | `cambio` 应为 0 |
| `[route] formato N: cod5 == nfsmw` | 格式表校验 | 应全部一致 |
| `[setkey] ... orden 7,7,6,6,...` | 描述符集键与绑定顺序 | 每个 ps 的 key 唯一 |

## 十一、一句话总结

**渲染器的逻辑是对的（格式、地址、绑定、数据全部验证过），坏的是 NVK 在 Switch 上的压缩纹理路径。**

下一步不是继续找"我们哪行写错了"，而是**绕过驱动的 BC 路径**或者**换 deko3d 后端**（后者需要重写整套图形后端 + SPIR-V→DKSH 着色器链，几周起步）。
