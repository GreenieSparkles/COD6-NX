# 第零章 · 当前症状（完整清单）

**当前版本：v302，卡上 md5 `AF94DE03`，能进关卡，不崩。**

## 0.1 卡顿（Stuttering）

**实测（`rex_stderr.log`，最新一次运行）：**

```
[native] slow frames: 3 over 50 ms, 2 over 100 ms;
         in them 555 pipelines, 7 shaders, 5 texture uploads, 0 render targets

[presentador] reparto de PaintAndPresent, 600 fotogramas (media/peor en ms):
  espera al envio de hace 3    4.04 / 20.12      ← 平均等 4 ms，最坏 20 ms
  reset del pool               0.01 / 0.02
  adquirir                    0.00 / 0.00
  tuberia                     0.00 / 0.02   (rehecha 1 veces)
  grabar                      0.07 / 0.31
  vkQueueSubmit               0.08 / 0.20
  vkQueuePresentKHR           0.28 / 0.70
  cierre                      0.01 / 4.70
```

**根因（有数据支撑）：**

| 卡顿类型 | 数据 | 原因 |
|---|---|---|
| **帧时间尖峰** | 100 ms 以上的帧里建了 **555 条管线** | **运行期翻译 + 编译着色器**，BO2 是构建期预编译 16,149 个 |
| **呈现等待** | 平均 4.04 ms / 最坏 20.12 ms 在等「三帧前的提交」 | 我们的呈现线程会阻塞游戏线程；BO2 是「只标记有新图，不阻塞」 |
| **池/管线重建** | `tuberia 0.00/0.02 (rehecha 1 veces)` | 偶发 |
| **帧率波动** | 菜单 60 fps，关卡 25~30 fps，重场景 5 fps | CPU 单帧 200+ ms |

## 0.2 画面差（Poor Visuals）

| 问题 | 数据 / 证据 | 状态 |
|---|---|---|
| **HUD / 字幕缺失** | 画面里没有准星、弹药、字幕 | 未查 |
| **远处地形不亮** | lightgrid 未编译生效 | 未查 |
| **远景发黑 / 闪烁** | 12 张 DXT 纹理实测 **mip 1~8 熵 0.00（全零）**，采样 mip>0 即黑 | 已定位原因，未修 |
| **贴图清晰度下降** | 因为有 `force_mip0` 兜底，所有纹理只采 mip 0 → 远处无 mipmap 过滤，闪烁 | 同上 |
| **火焰/粒子/枪口闪光** | dvar 列表保留了 `fx_enable`（未关），但受上面 mip 问题影响 | 部分 |

## 0.3 利用率不高（Low Utilization）

**实测（同一帧）：**

```
[native] per frame: renderer CPU 45.7 ms, GPU 26.0 ms over 1.0 submissions
[native-diag] per frame wall-time split:
              presentation call 9.8 ms (included in renderer CPU above),
              outside presentation 35.x ms
```

**CPU 45.7 ms 对 GPU 26.0 ms —— CPU 是 GPU 的 1.76 倍，意味着 GPU 有约 43% 的时间在空等。**

**CPU 时间去向（实测）：**

| 项目 | 每帧耗时 | 备注 |
|---|---|---|
| 呈现调用 | 9.8 ms | 包含在 45.7 里 |
| 呈现之外的渲染 | 35.x ms | |
| 纹理查询 | 4.9 ms | 其中哈希 2.2 ms |
| **顶点/索引哈希** | **8.3 ms** | **而顶点只拷了 0.4 MB —— 哈希比拷贝贵 80 倍** |
| 顶点拷贝 | 0.1 ms | 0.4 MB |
| 状态重建 | 29 次/帧 | |
| 纹理绑定重建 | 787~842 次/帧 | |

**对比 BO2（同一台机器、同一份 SDK 的 profile）：**

```
BO2 : 55~60 fps | CPU total 86%  | clocks CPU 1785 / GPU 768 / RAM 1600
COD6: 25~30 fps | CPU total 203% | clocks CPU 1326 / GPU 768 / RAM 1600
```

**换算式：BO2 每帧 6.2 个核百分点，COD6 13.7 —— 我们每帧烧的 CPU 是它的 2.2 倍。**

## 0.4 贴图闪烁（Texture Flickering）

**现象**：远处表面明暗跳动、纹理在两种样子之间闪。

**原因（已定位）**：

1. `cod6_native_force_mip0 = true` 把所有采样钳在 mip 0 → 远处产生严重锯齿和闪烁（这是**为了绕开 mip 全零而付的代价**）
2. mip 1+ 全零 → 一旦有采样落在 mip>0 就是纯黑，于是近处正常、远处忽黑忽亮

**证据**：`decode_mips.py` 对 12 张 DXT 逐层算熵：

```
s00_f18_256x256:  level 0  entropy 7.53   ← 真实图像
                  level 1  entropy 0.00   ← 全零
                  level 2..8  entropy 0.00
（12 张纹理无一例外）
```

## 0.5 贴图加载错误（Texture Loading Errors）★ 核心 bug

**现象（用户描述，最准确的一手信息）：**

> 「桌子加载了枪械纹理，还会随机变动」
> 「近处的石头，枪，瞄准镜，等等」
> 「任何版本的贴图都在逐渐走向崩坏」

**特征：**

- **任意物体**都可能显示**别的物体**的纹理
- **随机变化**（同一个物体不同时刻不一样）
- **近处也发生**（所以不是 mip 问题）
- **所有历史版本都有**（不是今晚引入的）
- 关掉录制线程照样发生

**已排除 12 种可能**，见第六章。

**两张渲染器路径的切换（`src/cod6_renderizador.cpp`）：**

```cpp
REXCVAR_DEFINE_STRING(cod6_renderizador, "xenos", "COD6", ...)   // 默认 xenos

if (REXCVAR_GET(cod6_renderizador) == "nativo2") {
  return cod6::native::CreateGraphicsSystem();       // 原生渲染器（快，但贴图串）
}
return std::make_unique<Cod6NativeGraphicsSystem>();  // SDK Xenos 模拟（慢，画面正确）
```

**注意：即使走 "xenos"，`Cod6NativeGraphicsSystem::CreateCommandProcessor()` 返回的也是 `NativeCommandProcessor`，它继承 `Cod6CommandProcessor` 并在 `WorkerThreadMain()` 里调 `VulkanCommandProcessor::WorkerThreadMain()` —— 所以 "xenos" 就是 SDK 的 Xenos 模拟路径。**

## 5.2 BO2 为什么好 —— 五个可量化的原因

### 原因 1：它有参照基准（最重要，别人抄不来）

BO2 的架构文档原话：

> **On the PC the SDK's exact Xenos emulation (Direct3D 12) is the reference image every renderer change is checked against.**

**它每改一行渲染器，都能和「正确图像」逐像素对比。我们没有这个流程 —— 这就是为什么一晚上改 10 个版本，每个都在猜。**

### 原因 2：构建期着色器，运行时零翻译

```
bo2zm_shaders.spvpack    1.68 GB    16,149 个预编译着色器
```

**我们：运行时翻译 → `slow frames: 3 over 50 ms; in them 555 pipelines`。**

**BO2 的 toml 里对应的是 `bo2zm_native_precompile` / `prewarm_pipelines` / `pipelines_save_in_match`。**

### 原因 3：263 个渲染器 cvar（我们 53 个），且优化默认全开

BO2 的 toml 写着：

```toml
# ---- Performance (the defaults are the tuned ones) ----
```

**255 项我们没有的机制，按我们的实测耗时归类：**

| 我们实测的耗时 | BO2 对应机制 |
|---|---|
| 顶点拷贝 8~55 ms | `vertex_cache`、`vertex_cache_mb`、`vertex_cache_by_writes`、`copy_neon`、`dedupe_vertices`、`index_cache`、`indices_neon` |
| **顶点/索引哈希 3~8.3 ms** | `hash_sampling`、**`hash_kb_per_frame`（每帧哈希预算）**、`vertex_cache_by_writes` |
| 纹理查询 5~27 ms | `texture_hash_thread`（专用线程，有 core/mb/priority）、`texture_bind_thread`、`upload_thread`、`texture_by_writes`、`im_load_without_memcmp`、`texture_reuse` |
| 状态重建 29 次/帧 | `canonical_key`、`fast_pass_key`、`dynamic_state3`、`block_register_writes`、`vector_register_writes`、`constants_ubo`、`constants_used`、`shared_constants_cache`、`pipeline_across_passes`、`direct_pipelines` |
| 全画不剔除 | `zcull`、`early_z`、`occlusion`、`occlusion_scale`、`cull`、`cull_prefetch`、`skip_invisible`、`plane_test`、`useful_area_pass`、`limiter` |
| 主线程做一切 | `deferred_recording`（录制线程）、`work_slots`、`prewarm_threads`、`compile_threads` |

### 原因 4：判断纹理变化用页写戳，不用哈希

BO2 的 NRO 里的原话：

```
Diagnostics (PC): log the code that writes the model lighting volume's pages
                  (the first 3D texture updated by pages). Off for play

{label = "TEXTURE CHECKS",
 hint = "FULL rechecks every texture's bytes instead of skipping unchanged ones. Try it "}
```

**默认行为是「跳过没变的」（写戳），全量重查只是排错开关。**

**我们：`native_hash.h` 里 `kSamples=8, kSampleBytes=64` —— 只看 512 字节，然后信任 8 帧。一张 256×256 DXT1 是 32 KB，我们只比对 1.6%。**

### 原因 5：读盘限速 + 专用呈现线程

```toml
# In a match the streaming pool is already full and the game keeps rereading the same
# images, so a low limit there helps: 4 MB/s gave about 4 % more frames in Town.
# bo2zm_ipak_mb_s_in_match = 4
```

**我们：`[io] rangos: 104 releidas de 154 (68 %)` —— 68% 是重复读，单次 10~45 ms。**

```
Present on the presenter's own thread instead of inside the thread that produces
the image. The game thread only marks that there is a new image and keeps recording,
so the GPU does not run out of work while presenting
```

**我们：`espera al envio de hace 3 4.04/20.12` —— 呈现线程阻塞游戏线程。**

### 附：BO2 还有 NVK 驱动级补丁

```
[nvk] c186 per-part draw measurement and improvements: available (NVK_SWITCH_DRAW)
[nvk] set 4 by differences (BO2ZM, build 184): available (NVK_SWITCH_DYN_UBO_DELTA)
[nvk] ZCULL: plane of 64224 bytes for depth 1280x1280 (align 1024)
```

**NVK（Switch 的 Vulkan 驱动）里有专门为 BO2 加的优化。我们是普通 NVK。**

## 9.1 ★ 贴图串到别的物体（核心）

**症状**：桌面显示枪械纹理、随机变动、近处也有、所有历史版本都有。

**已排除**：见第六章 1~12。

**两个最可疑方向（未证实）：**

### 方向 A：PM4 `SET_CONSTANT` 的常量块映射

`src/native/nativo/cod6_native_system_nativo.cpp:1773`：

```cpp
static uint32_t ConstantBase(uint32_t type_index) {
  switch ((type_index >> 16) & 0xFF) {
    case 0: return 0x4000;   // ALU
    case 1: return 0x4800;   // fetch
    case 2: return 0x4900;   // bool
    case 3: return 0x4908;   // loop
    case 4: return 0x2000;   // context
    default: return UINT32_MAX;      // ← 整包寄存器写入被丢弃
  }
}
```

**疑点 A1**：`default` 丢弃整包。若游戏用其他类型号写纹理 fetch 常量，那些写入永远进不了寄存器文件 → 绘制拿到上一个物体的纹理。
**疑点 A2**：`RegisterWritten`（`native_renderer.h:285` 附近）里 bool/loop 的范围是 `0x48C0..0x4927`，但这里映射到 `0x4900`/`0x4908` —— 两处对不上，说明这张基址表是**我们自己编的**，不是从 Xenia 抄的。

**验证**：对照 Xenia 的 `ExecutePacketType3_SET_CONSTANT`。

### 方向 B：着色器纹理槽位映射

`binding.fetch_constant` 来自 `shader->GetTextureBindingsAfterTranslation()`（`sdk/include/rex/graphics/pipeline/shader/spirv.h`）。若映射与实际槽位不符，绘制就采到别人的纹理。

## 9.2 mip 1+ 全零 → 远景黑/闪

**原因链**：

- 游戏用 **memexport 顶点着色器**把 mip 数据拷到目标地址
  - 我们自己 cvar 的描述：`"its texture streamer copies the low mips into place with it"`
  - BO2 的 NRO：`"BO2 copies streamed texture data (mip levels) this way."`
- 我们**无条件丢弃**这类绘制：

```cpp
if (vs->memexport_eM_written()) {
    REXLOG_INFO("... skipped.");
    return fail(2);      // 不看任何 cvar
}
```

- 所以 mip 从来没被写入 → 采样 mip>0 就是零

**`cod6_native_memexport_copy` 之前是空开关**（描述写着会做，代码从不检查）。v298 加了 CPU memcpy 实现但写坏 guest 内存，已回退 `false`。

**正确做法**（照 `sdk/src/graphics/vulkan/command_processor.cpp`）：

1. `draw_util::AddMemExportRanges(regs, *vs, ranges)` 取目标范围
2. 把该 guest 范围绑成 **SSBO**（Switch 统一内存，可零拷贝）
3. 正常绘制，让着色器自己写
4. 插 barrier

**不要**在 CPU 上猜一次 memcpy。

# 第十一章 · 必须遵守的规矩（血的教训）

1. **先读日志、先确认卡上是哪个 md5，再下结论。**
2. **每次分析用的日志必须和当次二进制一起归档。**
3. **任何「变快了/修好了」的说法必须有同关卡、同位置的对比数据。**
4. **改索引、改指针、改初始化时机之前，先核对 SDK 权威实现**（`sdk/src/graphics/vulkan/texture_cache.cpp`、`command_processor.cpp`）。
5. **不要在热路径里做初始化。**
6. **cvar 能不能从 toml 生效，要用日志里的实际值验证，不能假定。**
7. **MTP 卡只读优先，写之前先确认目标绝对路径。**
8. **关掉一个渲染 pass 之前，先确认它的输出没有下游采样**（COD5 的坑：跳过阴影渲染但着色器仍在采样 → 采到垃圾）。
